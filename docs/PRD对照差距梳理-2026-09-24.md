# 《实验流程智能化编排与执行平台_产品需求文档》对照差距梳理

日期：2026-09-24。对照对象：仓库 `multi-protocol-simulators` 分支（最新提交 `095196f`）。
方法：逐章阅读 PRD 2.2.0 – 2.2.26，对每一条能力在代码中找实现（文件:行），按「已支持 / 部分 / 缺失」标注。
本文只记录事实与差距，不改代码。文中路径相对仓库根目录。

## 0. 总体结论

1. **执行内核、资源约束、数据完整性这条线是强项。** 六类节点的状态机、依赖图并行推进、按能力选设备、检查点与重启对账、执行门、载具位置与可执行转运、多协议驱动（HTTP 网关 / SiLA 2 / Modbus TCP / OPC UA）、库存三量、复核与正式统计、报告固化、审计与电子签名，都已实现且有回归测试。PRD 2.2.5（资源预检查）、2.2.7（执行控制的启停）、2.2.9（样本与载具追踪）、2.2.12/13（采集与校验）、2.2.16（审计）大体达标。
2. **「编排」这一层是最大短板。** PRD 2.2.3 要求的可视化流程设计器目前是一行卡片加勾选框，没有连线、没有泳道；控制流只有顺序与分叉汇合，没有条件分支、循环、事件等待、步骤级超时 / 重试、跳过、跳转、异常处理节点、子流程。节点类型只有 6 种，PRD 列了 5 大类约 30 种。
3. **「智能调度」名不符实。** 现有排程器是多约束的贪心放置 + 顺序优化（局部搜索 / CP-SAT 候选），约束覆盖好，但没有可选调度模式、不读交付时间、没有任何事件触发的自动重排；设备故障后只报警并等人。
4. **「异常引擎」基本没有。** 现在的哲学是「结果不确定就停下交给人」，这在安全上是对的，但 PRD 2.2.11 要求的分类字典、策略库、自动 Retry / Reroute / Reschedule、设备热替换、事件中心影响面，一项都没有。
5. **任务层是扁的。** 实验任务与批次一对一，任务之间没有依赖，没有子任务，没有子流程，多批次优化只排顺序不认任务间先后。PRD 2.2.4.2 的「任务 → 子任务 → 节点 → 设备动作」任务树不存在。
6. **仿真、开放事件接口、AI 层缺失。** `domain/simulation.py` 是模拟设备的测量值生成器，不是执行前预演；没有出向 Webhook / 事件总线；没有任何模型或推荐能力，闭环实验只是「托管外部优化器的提案」。
7. **有几处代码或文档声称了但没实现的能力**，见第 4 节，建议先清掉，避免验收时被当作缺陷。

### 2.2.3 实验流程与方法创建 —— 重点章节

**设计器形态（`web/src/features/recipes/RecipeEditorPage.tsx`）**

- 画布是 `display:flex` 的一行卡片（`index.css:279-282`），按列表顺序排，两端固定「开始」「结束」。
- 卡片之间的 `.fedge` 是 56px 的 CSS 装饰线，画在相邻卡片之间，不画在真实前驱之间（`index.css:299-302`）。
- 分叉与汇合只体现为卡片上的「依赖 1、3」文字标签与一个 `branch` 样式类（`RecipeEditorPage.tsx:602-610`），没有并行泳道，没有分叉线与汇合线。
- 前驱通过属性面板里的勾选框设置（`DependencyEditor`，`:1293-1350`），只能勾选排在前面的步骤，且步骤保存后才有 `step_id` 可被引用。
- 拖拽只做列表重排（原生 HTML5 drag，`moveStep` 数组 splice），不能拖线连接。
- 没有引入任何图形库（`web/package.json` 只有 react / react-dom / react-router-dom），也没有 SVG。
- 批次运行视图是表格（`BatchDetailPage.tsx:146-200`），没有实时流程图。

**控制流构造**

| PRD 2.2.3.1 | 状态 | 现状与差距 |
|---|---|---|
| 顺序执行 | S | 默认 |
| 并行执行（分叉 / 汇合） | S | `after:[step_id]`，列表即拓扑序，结构上无环（`domain/graph.py`）。推进时一步完成开出所有前驱完成的步骤，汇合按 `join:{step_id}` 去重并取批次行锁（`workflow_service.py:388-472`）。绑定载具时并行设备步骤按板串行 |
| **条件分支** | **A** | 无 if / switch 节点，无边条件。最接近的是质检关卡：过 → 继续，不过 → 返工 / 报废 / 保持，不能在多条分支间选择 |
| **循环** | **A** | 只有关卡返工回到 `rework_to`，最多 1–5 次后转人工 |
| 等待 | P | 只有固定时长；「业务事件」等待被显式拒绝（`steps.py:139-142`），因为没有发事件的入口 |
| 定时 | P | 没有绝对时间触发节点；有排程给指令的最早投递时刻 `not_before` |
| **超时（步骤级）** | **A** | 没有任何代码读取步骤 `timeout` 字段（`models/recipe.py` docstring 提到但未用）。设备指令超时按 `dur × 系数 + 宽限` 或能力 `recovery.maxRunMin`，超过转结果未知等人，不自动处理；人工步骤 `due_at` 只用于排序 |
| **重试（步骤级策略）** | **A** | 无步骤级重试次数 / 间隔；只有能力级 `recovery.retryable` 决定「允许人点重试」 |
| **跳转** | **A** | 只有关卡返工目标 |
| 人工确认 | S | 人工节点（表单 / 签名 / 资质）+ 审核节点（角色 / 职责分离 / 驳回回到上游人工步） |
| **异常处理节点** | **A** | 失败一律 `batch.state=fault` → 恢复评估（续跑 / 重试 / 终止） |
| **子流程调用** | **A** | 步骤无方法引用字段；全库无 sub_recipe / subflow / 子流程 |

**节点类型（PRD 2.2.3.2）**

| PRD 大类 | PRD 举例 | 现状 |
|---|---|---|
| 实验节点 | 加液 / 混匀 / 离心 / 孵育 / 洗涤 / 分液 / 转移 / 检测 / 数据分析 | 统一为「设备节点 = 能力 + 参数」；能力字典可扩展，但节点没有实验语义子类型，画布上看不出是加液还是离心 |
| 设备节点 | 调用设备 / 执行方法 / 获取状态 / 设置参数 / 获取结果 | 只有「执行设备动作」一种；指令类型固定为 dispatch / resume / retry / hold / abort / transfer，没有「读状态」「设参数」「取结果」节点 |
| 机器人节点 | 取样 / 放样 / 搬运 / 转运 / 上下料 | 转运不是节点：批次绑定载具后由系统在设备步骤前自动插一条 `transfer` 指令。设计器里画不出、也控制不了机器人动作 |
| 系统节点 | 数据采集 / 数据校验 / 条件判断 / API 调用 / 文件处理 / 消息通知 | 只有质检关卡（阈值判定）与样本拆分；无 API 调用、文件处理、消息通知节点 |
| 人工节点 | 人工操作 / 确认 / 放行 / 异常处理 | 人工、审核、关卡人工放行已有；无「人工异常处理」节点 |

**方法管理（2.2.3.3）**：PRD 要求「流程负责做什么、方法负责怎么做」两层分离。现在 `Recipe` 一个对象同时是流程和方法，设备步骤直接带参数；没有独立的「设备方法」对象（仪器型号 + 方法名 + 方法版本 + 设备程序 + 数据输出规则）。驱动也不能自报支持的方法目录（`adapters/registry.py:66-77` 只返回 hold/abort/query/dedup 标志）。

**参数化流程（2.2.3.4）**：S（部分形态不同）。同一方法通过方案条件矩阵生成不同孔位参数，冻结进 `plan_snapshot.condition_params`，下发时 `params.wells` 带全部孔位参数。差别在于：PRD 说的是「不同实验任务 / 实例」，现在是「同一批次内不同孔位」，一个方案只能出一个批次。

### 2.2.20 / 2.2.21 数据模型与状态模型
