# 设备接入插件化：配置热生效、设备接入模板、接入验收闸门、设备模块

日期：2026-09-29。
起因：MADSci 对照评审（[MADSci对照评审-2026-09-28.md](MADSci对照评审-2026-09-28.md)）建议把现有测试积累整理成设备接入验收工具包，
并按「真实接口、模拟接口、类型、测试、部署文件一起交付」组织设备模块；随后的问题是：设备接入能不能改成插件式、页面配置、热插拔，
不要每次改都重启。

## 1. 结论

「插件」拆成两件事做，风险完全不同：

- **设备怎么映射**（点位、命令模板、状态码、参数对应）：页面配置，改完下一轮执行器就用上；同一类设备存成**设备接入模板**。
- **新协议怎么通信**（厂家 SDK、私有协议）：一定是代码，放在 ILCS 之外的**设备模块**（独立网关，经 `http_json_v1` 接入），
  不从页面上传代码、不在执行器里热加载。

| 做法 | 适合 | 热插拔 | 结论 |
|---|---|---|---|
| 设备接入模板（纯配置数据） | 能用现有映射驱动描述的设备 | 能 | 做了 |
| 设备模块（独立网关，`sdk/ilcs_gateway`） | 新协议、厂家 SDK / DLL | 能：起服务、页面登记 | 做了 |
| 进程内插件包（启动时加载） | 必须和执行器同进程的驱动 | 半热：重启 api 与执行器 | 暂不做 |
| 页面上传代码、执行器热加载 | — | 能 | 不做 |

不做最后一种的原因：执行器是单活进程、握着全站在途指令，插件里一个 C 扩展崩溃就是全站执行门关闭；`importlib.reload` 不替换已建的实例，
C 扩展不能重载；上传代码绕开代码评审，审计答不出「这条指令是哪一版驱动执行的」；grpc / protobuf 被 OR-Tools 钉在 1.81 / 6.33，
厂家 SDK 自带的版本多半装不进同一个进程。

## 2. 做之前核对到的现状

- 改配置本来就不用重启：保存时 `config_version` 加 1，执行器每轮读库、驱动实例按 `config_version` 缓存（`adapters/registry.py`）。
- 真正要重启的：新设备换了地址要改 `ILCS_ADAPTER_ALLOWED_HOSTS`（只认完整主机名、启动时读一次）；加驱动、改驱动代码要重建镜像。
- 两个缺口：
  - 在途指令期间改配置没有拦。设备侧去重的驱动查不回原指令，批次判故障转人工；走作业台账的映射驱动台账按工位存、不按地址，
    换地址后会拿旧作业去读新地址的状态，读到空闲就判完成——假完成（读代码推断，修复后有测试守着拦截）。
  - 保存时不校验配置，配错了要到测试连接或执行器实例化时才发现。

### 闸门的规则

- 第一次接成真实设备、换了驱动：欠**动作级**；其他改动欠**只读级**；还没补上的动作级不因为又改了一次而降级；模拟适配器不设闸门。
- 欠着就进执行门的 `blocked_stations`（并单列在 `acceptance_pending`）：排程绕开、下发与续跑 423；已在队列里的动作指令在验收排队时等，
  没有排队的验收（上次不通过、欠动作级）时不投递、挂起批次。
- 改完配置执行器自动排一次只读级；自报为模拟器的设备只读级就能清掉动作级要求（不会造成物理后果、正式环境也不许接入）；
  设备当时连不上导致没通过的，恢复在线后自动再排一次。
- 动作级要签名并写明现场批准人；等工位上没有可能在动作的指令才开始，排队期间新的动作指令先不投递。
- 迁移前在用的配置不追溯。

### 复查后补上的约束

- **动作级验收和动作指令守同一道门**：执行门开着、设备在线且心跳新鲜、没有联锁、接受指令、工位上没有在动作的指令，才开始；
  同时进行的动作级验收不超过执行器并发数的一半。等待的原因写在排队记录上（界面「结论」列显示「等待：…」）。
  串行模式（`ILCS_EXECUTOR_MODE=serial`）不跑动作级：几分钟的动作会拖住别的工位的保持与终止，排队等切回并发模式。
- **续跑不等动作级验收**：它接续的是验收之前就在设备上保持着的作业，动作级验收本来就在等它结束，两边互等谁也动不了。
- **验收留下的指令**：验收结束时还有没结束的 ACC- 指令，先逐条终止；终止不了或状态查不清的，报告「清理」项不通过，
  工位改回欠动作级（设备可能还在动），现场核查后重新验收。动作级验收中途出错、被执行器重启打断的，同样改回欠动作级；
  只读级被打断的不改欠的级别，按当前配置自动重排（只读级不让设备动作，留不下什么）。
- **领取时核对配置版本**：排队之后配置又改了的，这条作废、按新配置重排；结论按最新的适配器行落到闸门上，
  验收期间配置变了的报告不能替新配置放行。验收自己建驱动实例，开始前关掉执行器缓存的实例（保持连接的设备不能被两个连接占着）。
- **签名放行**：检查清单证明不了的设备（不支持按指令号查询、动作要现场摆位），现场核对后签名放行
  （`POST /stations/{id}/adapter/acceptance/waive`，签名针对工位与当前配置版本，写明依据），放行作为一条验收记录存档。
  动作级申请的签名同样针对工位与当前配置版本；申请与放行都先锁住适配器行，同时申请只排得进一条。
- **只改说明、协议名、版本、超时这类字段**（不改变连谁、怎么判结论）：不断开设备、不重置在线状态，也不新欠验收；
  原来欠着的照旧欠着，排队中的旧验收作废、按新版本重排。停用 / 启用不算这一类。
- **模板职责分离**：起草人与改过草稿的人都不能发布它；发布后内容与审批证据由触发器冻结，状态只能已发布 → 退役。
  模板的列表、详情与导出只给维护工位（`station.edit`）与发布模板（`template.release`）的人看（里面是点表、命令与内部地址示例）。
- **工位只填连接参数**：套用模板时工位能填的只有驱动登记的连接参数（组合工位按路由名填各路由的连接参数与凭据引用），
  映射改动一律走模板修订与另一个人发布。模板与工位配置里都不能出现秘密原文，包括写在地址里的口令（`scheme://用户:口令@主机`）。
- **白名单与请求地址**：像数字又不是合法 IP 的主机（`127.1`、`0x7f000001`）一律不认；IPv4 映射地址按它连的 IPv4 比；
  正式环境不接受嵌入 IPv4 的 IPv6 网段。HTTP 驱动拼出的请求地址必须仍是 `base_url` 那台主机，映射里写完整网址的路径被拒绝。
- **网关 SDK**：HTTPS 必须带令牌；明文 `--insecure` 缺省只监听 127.0.0.1，不带令牌不许监听别的地址；令牌、私钥、台账创建时即属主只读；
  终止一个启动没拿到应答、设备侧也还没找到的作业回结果未知，不谎报已停。

### 与评审建议的差异

- 评审只要求一个验收脚本（9.1 已做）；这次把验收挪进执行器、报告入库、配置变更后当闸门——否则「热生效」就等于「改完没人验证」。
- 「驱动自报完整契约、升级时列出受影响的方法」（评审 9.6）没做：模板有版本与摘要、验收报告带驱动 / 固件 / 配置 / 模板版本，
  但参数与输出定义还没从驱动自报、没和设备方法逐项核对。
- 真实设备的回执丢失仍要在网络路径上注入（中间代理），验收工具不提供代理。

### 部署核对时补上的（本机对 11 个试点模拟设备逐台跑动作级 + 故障项目）

自动的只读级 11 台全部通过；逐台手动跑动作级 + 故障项目时发现清单对几类设备会误判，已改：

| 现象 | 原因 | 处理 |
|---|---|---|
| PLC 点表（ST-02、ST-03）、中间表（ST-01-B）「回执丢失」不通过 | 点表写下启动沿 PLC 就动作，协议层没有回执可丢；中间表插入作业行就是交接 | 模拟设备控制口报 `unsupported`，清单判跳过 |
| 设备忙、联锁被前一条探针挡住（「正在执行 ACC-…」） | 丢回执的探针还在跑，单作业设备对新指令一律报忙 | 探针先等结束（或终止）再测后面的；受理了的探针都记下，收尾逐条终止 |
| 中间表设备忙、联锁不通过 | 拒绝是设备侧轮询到作业行后回写的 | 提交只是交接的驱动（`handoff = "async"`）等它回写成失败、设备没动作 |
| PLC 点表设备忙时一直没结论 | PLC 只报故障码、停在空闲，驱动等启动超时才判结果未知 | 点表新增 `start_refused`：登记的故障码 = 设备明确拒绝，判失败 |
| 中间表失联判不出来 | 按心跳超时（30 秒）判失联，断开 3 秒看不出来 | 驱动报判定时延 `offline_after_sec`，失联项目断开得比它久 |
| OPC UA（ST-03、ST-04）失联后一直不恢复、验收留下残留 | 模拟器停服务时 asyncua 先等客户端处理任务收完才关监听（客户端在重连就一直关不掉），超时后重启线程直接退出 | 模拟器「断网」先关监听、断开已有连接再收尾，收尾超时照样重启（失败重试）；失联后等断开时长过去、连续两次答得上来再收尾 |
| 两台 AGV 同时验收，一台的验收中断（「设备接口不可达」） | 两台车共用一个车队接口，另一台的失联项目把接口断开了；轮询时一次查询没连上就让整次验收出错 | 轮询时一时连不上记「不可达」接着查，超时前恢复照常出结论 |
| 中间表（ST-01-B）失联判成连接错误、收尾查不到探针 | 失联项目每 0.2 秒新建一个驱动实例探测、从不关：中间库连接被占满（PostgreSQL 缺省 100） | 探测用完就关；清单结束关掉它建的所有驱动实例；回归用例数同时开着的实例 |
| 车队（AGV）保持之后任务一直排队 | MiR 的保持是整机暂停，终止任务不会让它回到就绪 | 保持项目改为先续跑到做完，续跑不了再终止 |
| 车队「正常完成」提交被拒 | 转运要起止位置，工位极限里没有；验收指令按普通动作指令发，驱动不认载具、起止位置参数 | 验收缺省改为模板的验收缺省 → 适配器配置 `acceptance` → 极限中点；试点预设给 AGV 登记了起止位置；转运能力的验收指令按生产上的转运指令发（type = transfer）；界面可填 JSON 参数 |
| 充放电柜（ST-07）「正常完成」超时 | 模拟循环 60 秒，每项只等 60 秒 | `ILCS_ACCEPTANCE_POLL_TIMEOUT_SEC` 缺省改为 180 秒 |

这些情况都有回归用例：`tests/domain/test_device_acceptance.py::test_every_pilot_simulator_passes_the_full_checklist`
（PLC 点表 OPC UA / Modbus、OPC UA TaskExecution、车队、中间表各跑一遍完整清单，不许有误判的不通过或残留，
同时开着的驱动实例不超过 12 个、结束时全部关掉）。部署后按界面那条路（签名申请 → 执行器执行）对每台试点设备复核一遍
动作级 + 故障项目；点表与中间表的「回执丢失」应判跳过。

  验收入库与闸门 7 个（`tests/api/test_acceptance_runs.py`）、统一控制口与不连库的验收命令 4 个（`tests/domain/test_device_acceptance.py`）、
  驱动目录与模板 6 个（`tests/api/test_device_templates.py`）、设备模块 3 个（`tests/api/test_device_modules.py`：样板自测、脚手架生成的模块开箱即绿、
  profile.json 导入 → 另一人发布 → 工位套用 → 执行器跑只读级与动作级 + 故障项目全部通过）。
- 样板模块自测 6 个（`device-modules/sample-cycler/tests`），不连 ILCS 数据库。
- 前端类型检查与构建通过，构建产物输出到临时目录。界面没有在浏览器里走查（预览启动器读不了 `~/Documents` 下的项目）。

## 5. 部署注意

- 两版迁移（`0040`、`0041`）只加表、加列，不删列；照常 `docker compose run --rm migrate`。
- 试点：先建 `secrets/simctl`（属主 10001）再 `up`——没建或属主不对时控制口不开，设备照常模拟，验收的故障项目标跳过。
  `pilot-devices.json` 新增了 `simulator_control`，要重新 `configure-pilot-adapters.py apply --preset` 才写进工位；切换后执行器自动跑只读级验收。
- `ILCS_ADAPTER_ALLOWED_HOSTS` 可以改写成设备网段（如 `10.20.1.0/24`），以后同网段新设备不用再改。
  试点要追加 `sql-sim-slurry-b`：中间表工位的故障注入走设备侧进程的统一控制口，不在白名单里切换脚本一个都不改。
- 新权限 `template.release`（发布与退役设备接入模板）缺省给 QA、自动化工程师、管理员；组织存过权限矩阵的，新权限按缺省补上。
