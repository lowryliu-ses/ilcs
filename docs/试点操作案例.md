# 试点操作案例：电解液 FEC × 注液量，跑在两台 SiLA 2 设备上

对着本地 **http://127.0.0.1:8090** 或远端 **http://10.10.106.51:8090** 做，两边数据一致。演示账号口令一律 `ilcs1234`。

[操作案例.md](操作案例.md) 讲的是基础闭环：资质、校准、SOP、方法、方案、任务、批次、数据复核、报告。这份讲的是接上真实协议设备以后的自动化链路：

- **方法**：修订已发布的方法，加一个质检关卡。
- **方案**：矩阵因子按孔位下发到设备参数，并设定设计空间。
- **任务 → 批次 → 排程**：物料预留、资源时间窗、开跑检查、签名下发。
- **执行**：指令真的经 gRPC + TLS 发到外部 SiLA 2 设备；设备回报的实际注液量直接入库存。
- **质检关卡**：不合格自动返工，返工仍不合格转 QA 判定。
- **多通道**：8 通道充放电柜上两个批次并行。
- **故障演练**：联锁、设备掉线、回执丢失，看系统怎么挡、怎么不重发。
- **闭环**：导出训练数据，外部优化器提交下一轮提案，系统校验后生成待审批草稿。

**只想看结果**：执行下面这条命令。它会备份并清空演示库、重新播种主数据、删掉其余演示方法与方案，然后按本案例把数据真实跑一遍导进去：批次由执行器投递到两台 SiLA 2 模拟设备，签名由脚本代签，审计里注明「案例导入脚本代签」。本地执行时在命令前加 `ILCS_ROOT=$PWD ILCS_BACKUP_ROOT=$PWD/data/backup`。导入后阶段 6、7（多通道、故障演练）仍需手工操作。

```bash
sudo bash /opt/ilcs/scripts/reset-pilot-case.sh
```

建议开两个浏览器窗口（普通 + 隐身），一边登 `researcher` / `operator`，一边登 `qa`。主线约 30 分钟，故障演练另需 15 分钟。

## 账号与职责

| 账号 | 在这个案例里做什么 |
|---|---|
| `researcher` | 修订方法、建方案、设计空间、建任务、提交提案 |
| `qa` | 批准并发布方法、批准方案、质检判定、结果复核 |
| `operator` | 接单、建批次、排程、下发、现场核查 |

多处规则是「提交人 ≠ 审批人」，同一个账号做不完。

## 设备

| 工位 | 在方法里的步骤 | 接的设备 | 行为 |
|---|---|---|---|
| ST-05 真空干燥与称重站 | s01 真空干燥、s02 称重选片 | 系统内置模拟适配器 | 立即完成 |
| ST-06 手套箱组装线 | s03 注液封口组装 | **SIM-LH-01**（外部 SiLA 2 配液设备） | 每个任务约 20 s；按孔位注液，回报每孔实际量（±0.5%）并折算电解液消耗 |
| ST-07 充放电测试柜 | s04 首次充放电 | **SIM-CYC-01**（外部 SiLA 2，8 通道） | 每个任务约 60 s，占 1 个通道；回报 `discharge_capacity_mAh` ≈ 3.2（±0.5%） |

s01/s02 很快做完后，系统会把下游时间窗整体提前（不与别的批次冲突时），所以不用干等方法里写的 60 分钟干燥。

## 阶段 0：看一眼设备是真的接上了（任意账号）

1. **资源管理 · 工位配置**：ST-06、ST-07 的驱动是 `sila2_v1`，状态在线，ST-07 通道数为 8。
2. 页面顶部的执行门应为开放、无阻塞工位。
3. 想看设备侧：在 `deploy/` 目录（远端是 `/opt/ilcs/deploy`）执行下面的命令，能看到执行器每 10 秒读一次设备身份（`DeviceIdentity`）。

```bash
docker logs --tail 5 ilcs-sila-sim-lh
```

> SiLA 设备不往系统推心跳。「在线」是执行器主动探测得出的结论，探测不到就判失联，不沿用旧状态。

## 阶段 1：修订方法，加质检关卡（`researcher` → `qa`）

`researcher`：

1. **实验设计 · 实验流程** → 进 `R-205 扣电组装与首次充放电` 的详情 → **新建修订草稿**。提示会给出新编号（形如 `R-205-r1`），下面称它为「修订版」。
2. 进修订版的 **图形化编辑**。节点面板点 **+ 质检关卡**，放在最后（s04 之后），按下表设置：

| 字段 | 填什么 | 为什么 |
|---|---|---|
| 测量来源（之前的设备步骤） | `首次充放电测试` | 读这个步骤的设备回执 |
| 测量字段 | `discharge_capacity_mAh` | 充放电柜回报的放电容量 |
| 下限 | `3.25` | 故意设得比模拟器的 ≈3.2 高，让它不合格 |
| 判定范围 | 整批（一个测量值） | |
| 不合格去向 | 返工 | |
| 返工回到 | `首次充放电测试` | |
| 最多返工次数 | `1` | |

   想看「一次通过」的路径，把下限改成 `3.1`。

3. **保存草稿**，看右侧校验清单都通过。可以试着把「返工回到」选成关卡之后的步骤，或把测量来源选成人工步骤，校验会逐条拒绝。
4. **保存并提交评审**。

`qa`：

5. 修订版详情 → **批准** → **发布**，两步都要签名。
6. 先用 `researcher` 点批准试一次：作者和提交人不能批准自己的方法。

## 阶段 2：矩阵方案，因子下发到设备参数（`researcher` → `qa`）

`researcher`：

1. **实验设计 · 实验方案** → **新建方案**，名称 `FEC × 注液量 试点`，实验流程选修订版，类型选 **矩阵实验**。
2. 详情页 → **编辑因子**：

| 因子 | 单位 | 水平 | 作用于设备参数 | 物料换算 |
|---|---|---|---|---|
| `FEC 含量` | `%` | `0, 2, 5, 10` | 不作用于设备（仅区分样本） | — |
| `注液量` | `μL` | `50, 60` | `注液封口组装.electrolyte` | `电解液 LP57`，每单位 `0.001` mL |

   重复数 `1`，共 4 × 2 = 8 个条件，正好占满 ST-06 的 8 个位置。

3. 保存后看两处：
   - **物料需求预览**：电解液约 0.44 mL（4 × (50 + 60) μL）。
   - 「作用于设备参数」列显示 `注液封口组装.electrolyte`。建批次时，每个孔位的注液量会冻结进快照，**一条指令带全部孔位参数**下发。水平超出 ST-06 的 electrolyte 范围（10–200）时校验会拦住，可以试着填一个 `300`。
4. 下方「闭环实验」面板 → **编辑设计空间**：FEC 含量 `0 … 10`，注液量 `40 … 80`，禁止组合填 `[{"FEC 含量": 10, "注液量": 40}]`，每轮最多 `8`。设计空间**只能在审批前改**，批准后随方案冻结。
5. **锁定矩阵** → **提交评审**。

`qa`：

6. **批准**（签名）。

## 阶段 3：任务、批次、排程、下发（`researcher` → `operator`）

`researcher`：

1. **工作台 · 任务中心** → **建立任务**，方案选 `FEC × 注液量 试点` → 分配给 `操作员`。

`operator`：

2. 任务中心 → 接单。
3. **执行与监控 · 批次管理** → **新建批次**，选方案和刚接的任务。**资源管理 · 试剂耗材** 里 `LOT-ELY-0611 电解液 LP57` 的可用量少了 1 mL（BOM 预留），账面库存不变。
4. 批次列表点 **排程**。去 **执行与监控 · 排程** 看 ST-05 → ST-06 → ST-07 的时间窗，带「硬」标记的是硬间隔约束（称重后 20 min 内必须注液）。
5. 批次详情 → **开跑检查**：九项逐条给结论。ST-06/ST-07 显示在线，是因为探测成功，不是配置写的。
6. 勾「已完成人工复核」→ **签名并执行**。

## 阶段 4：看它跑（`operator`，主要是观察）

打开批次详情，停在「指令与检查点」面板，每隔十几秒刷新一次：

| 时刻 | 你会看到 |
|---|---|
| 下发后几秒 | s01、s02 完成（内置模拟），下游时间窗按实际进度提前，审计里有「按实际进度提前」 |
| s03 | 指令发到 ST-06，状态依次为已发送 → 设备已接受 → 执行中 → 已完成（约 20 s） |
| s03 完成 | **试剂耗材**：LP57 按设备回报的实际量扣减（约 0.44 mL，不是 BOM 的 1 mL）。偏差超过 5% 照常入账，但应在 **报警处理** 出现一条消耗偏差报警、标记待复核：账上记设备实测量，计划量只作对照 |
| s04 | 指令发到 ST-07，占一个通道，约 60 s |
| 质检关卡 | 读到约 3.2 < 3.25，不合格 → 返工：s04 重做一次，旧的 s04 记录标为「已被返工取代」但保留 |
| 返工后 | 仍不合格，返工次数用完 → 新的关卡记录为「待办」，批次「已保持」，等 QA |

界面的指令表只列状态。想对比下发的设定值和设备回报的实测值，查批次详情接口里的检查点（`TOKEN` 的取法见阶段 8.3，账号换成 `operator`，`BATCH_ID` 换成批次编号）：

```bash
curl -s $BASE/batches/BATCH_ID -H "Authorization: Bearer $TOKEN" | python3 -c 'import sys,json; [print(c["step_index"]+1, c["payload"]["station_id"], c["payload"]["origin"], "\n  下发:", c["payload"]["params"], "\n  实测:", c["payload"]["delivered"]) for c in json.load(sys.stdin)["checkpoints"]]'
```

- s03（ST-06）：下发的 `wells` 是每个孔位 `{"electrolyte": 50}` 或 `60`，一条指令带全部孔位参数；实测的 `wells` 是每孔实际注液量（偏差在 ±0.5% 内），`materials` 是折算后的电解液消耗。
- s04（ST-07）：实测里有 `channel`（占用的通道）和 `discharge_capacity_mAh`，质检关卡读的就是这个值。
- 来源：SiLA 工位是 `real:sila2_v1`，ST-05 是内置模拟。

在设备侧确认每条指令只动作了一次：

```bash
docker compose exec sila-sim-lh python simulators/sila_device/fault.py state
docker compose exec sila-sim-cycler python simulators/sila_device/fault.py state
```

`executions` 里每个指令号都应是 `1`。充放电柜会有两条：原始一次加返工一次，是两个不同的指令号。

## 阶段 5：QA 判定质检关卡（`qa`）

1. 批次详情里，保持中的关卡旁有 **质检判定**。
2. 先用 `operator` 点：会被拒，质检判定只允许 QA。
3. 换 `qa`：结论「放行」，判定依据写清楚（例如「复测 3.22 mAh，下限设定过严，按工艺偏差单放行」）→ 签名。批次随后完成。
4. 判成「不合格」就按报废处理：批次故障，样本全部失败。

## 阶段 6：多通道并行（`operator`，可选）

1. 用同一方案连着建两个批次（任务可以不选），都排程、都下发。
2. **排程** 页：两个批次在 **ST-07 上时间窗重叠**，8 个通道允许并行；在 **ST-06 上前后错开**，它只有 1 个通道。
3. 执行时用 `fault.py state` 看充放电柜的 `busy_channels`，会同时出现两个通道。

## 阶段 7：故障演练（`operator` + 命令行）

在 `deploy/` 目录执行，模拟器容器里自带注入命令。**每项演练完都要执行 `none` 恢复**，故障是持续生效的。

### 7.1 公共保护联锁 → 全站停

```bash
docker compose exec sila-sim-lh python simulators/sila_device/fault.py interlock
```

约 10 秒后，页面顶部执行门变为**关闭**，原因是「ST-06 公共保护联锁未解除」。此时排程、下发、续跑一律被拒，保持和终止仍可执行。联锁是现场公共安全事实，哪台设备报了都是全站停。

```bash
docker compose exec sila-sim-lh python simulators/sila_device/fault.py none
```

### 7.2 设备掉线 → 只挡这一个工位

```bash
docker compose exec sila-sim-lh python simulators/sila_device/fault.py offline 60
```

模拟器真的停掉 gRPC 服务 60 秒。执行门仍是开放的，但 ST-06 被列为阻塞工位（「适配器失联」）：用到 ST-06 的批次下发被拒，别的工位照常。60 秒后探测恢复，自动转回在线。设备内部在跑的任务不受影响，恢复后系统按原指令号查回结果。

### 7.3 回执丢失 → 结果未知，不重发

这是最关键的一项：设备其实已经在动，但系统没收到回执。

1. 建一个新批次并排程，**先不下发**。
2. 注入故障：

```bash
docker compose exec sila-sim-lh python simulators/sila_device/fault.py lost_receipt
```

3. 下发。s01、s02 照常完成；s03 的指令变成 **结果未知**，批次转故障挂起。之后执行器跑多少轮都不会重发这条指令，因为重发一次注液的代价不是一条日志。
4. 先恢复模拟器，再核查：

```bash
docker compose exec sila-sim-lh python simulators/sila_device/fault.py none
docker compose exec sila-sim-lh python simulators/sila_device/fault.py state
```

   `executions` 里这条指令是 `1`：设备只动作了一次。

5. 界面上这条指令旁点 **现场核查**，按「到现场看到的」下结论并签名：
   - **已执行**：按人工核实写检查点，流程继续。
   - **未执行**：设备确认没有动作，可在恢复评估里续跑或重试。
   - **部分执行**：物理状态不可复现，只能终止。

其他模式（`slow_submit`、`stuck`、`fail`、`partial`、`busy`、`clock_skew`、`no_dedup`）的含义和系统应有的反应，见 [simulators/sila_device/README.md](../simulators/sila_device/README.md)。

## 阶段 8：数据与闭环（`researcher` + `qa`）

### 8.1 让结果成为「正式结果」

照 [操作案例.md](操作案例.md) 阶段 3.1–3.3：给批次样本建检测任务、录入 **首次放电比容量**，再由 `qa` 逐条复核，并给质量判定（有效 / 无效）。**只有复核通过且质量有效的结果**才会进入训练数据。

### 8.2 导出训练数据

方案详情 → 「闭环实验」面板 → **导出训练数据**。CSV 每行是一个样本：因子列（`factor:FEC 含量`、`factor:注液量`）加指标值。待复核的、判无效的、已被新版本替代的结果都不在里面。

### 8.3 外部优化器提交下一轮

界面上没有「提交提案」按钮，这是故意的：提案来自外部算法。用研究员身份调一次接口，模拟优化器（`PLAN_ID` 换成方案编号，远端把地址换成 10.10.106.51）：

```bash
BASE=http://127.0.0.1:8090/api
TOKEN=$(curl -s -X POST $BASE/auth/login -H 'Content-Type: application/json' -d '{"username":"researcher","password":"ilcs1234"}' | python3 -c 'import sys,json;print(json.load(sys.stdin)["access_token"])')
curl -s -X POST $BASE/plans/PLAN_ID/proposals -H "Authorization: Bearer $TOKEN" -H "Idempotency-Key: $(uuidgen)" -H 'Content-Type: application/json' -d '{"proposal_id":"bo-round2-001","source":"BO-GP","model_version":"gp-2026.09","rationale":"EI 最大的 3 个点","points":[{"FEC 含量":1.5,"注液量":55},{"FEC 含量":3,"注液量":62},{"FEC 含量":7.5,"注液量":70}]}'
```

- 返回 `"state": "accepted"` 和 `created_plan_id`。进这个新方案：它是**草稿**，第 2 轮，父方案是本方案，条件就是这 3 个点（不做全因子组合）。它仍要锁定、提交，并由 QA 批准后才能执行。提案不会直接变成实验。
- 用同一个 `proposal_id` 重发：回放原结论，不会生成第二份草稿。
- 换一个 `proposal_id`，点改成 `{"FEC 含量":12,"注液量":60}` 和 `{"FEC 含量":10,"注液量":40}`：返回 422，逐点说明「高于设计空间上限 10」「禁止组合」。被拒的提案也会留档，在「收到的提案」里能看到原因。

正式对接时，优化器应使用服务身份调用 `POST /api/runtime/plans/{id}/proposals`，由管理员在服务身份上授予 `plan_proposals` 范围，不要用个人账号。

## 这个案例证明的规则

| 你会看到的 | 为什么 |
|---|---|
| 设备在线来自探测，掉线自动判失联 | 不编造心跳 |
| 一条指令带全部孔位参数，设备按孔位执行 | 矩阵条件真的到达设备，而不是只写在方案里 |
| 库存按设备实测量扣减，偏差报警但照常入账 | 账上记实测量，计划量只作对照 |
| 取不到测量值的关卡不放行 | 没有数值不等于合格 |
| 返工旧记录作废保留，QA 放行必须写依据并签名 | 可追溯 |
| 联锁全站停，掉线只挡单个工位 | 公共安全和单机故障分层处理 |
| 回执丢失不重发，由现场核查签名下结论 | 系统不替人猜设备动没动 |
| 提案只生成草稿，越界提案逐点拒绝并留档 | 闭环受设计空间约束，执行前仍要人审批 |
