# 真实设备适配器配置模板

系统把“协议显示名”“驱动键”“非秘密连接配置”“凭据引用”和“能力声明”分开保存。真实设备必须使用 `kind=real`，且 `driver` 必须对应后端已注册实现；缺少实现时健康检查和重连都会拒绝，绝不回落到模拟器。

## 先选驱动：设备给的是什么接口

| 设备 / 现场给的接口 | 驱动 | 指令号、去重、查询由谁负责 | 示例工位（`simulators/pilot-devices.json`） |
|---|---|---|---|
| 厂家或集成商按 ILCS 网关契约做了 HTTPS 服务；只有 Windows SDK / DLL 的设备由「厂家 SDK 接口服务」包成这份契约 | `http_json_v1` | 设备侧 | ST-07 充放电柜 |
| SiLA 2 服务器实现了 ILCS TaskExecution 特性 | `sila2_v1` | 设备侧 | ST-01-A、ST-06 |
| OPC UA 服务器实现了 ILCS TaskExecution 节点与方法 | `opcua_v1` | 设备侧 | ST-04 辊压冲切机 |
| PLC 按 ILCS 任务寄存器表编程 | `modbus_tcp_v1` | 设备侧 | —（本机模拟设备 `simulators/modbus_device`） |
| PLC / 视觉系统已有 OPC UA 服务器，节点是厂家自己的 | `opcua_map_v1` | 驱动作业台账（PLC 回显指令号时更可靠） | ST-03 涂布烘干线 |
| PLC / 温控仪表有自己的 Modbus 寄存器表（含串口转以太网后的 RTU 设备） | `modbus_map_v1` | 驱动作业台账 | ST-02 中试匀浆罐 |
| 仪器给了 RS232 / RS485 / TCP 命令手册（一问一答的文本命令）；机械臂仪表盘服务；固定式读码器 | `line_command_v1` | 驱动作业台账 | ST-05 的干燥箱、ARM-01 机械臂 |
| 梅特勒天平（MT-SICS，串口或以太网） | `mt_sics_v1` | 驱动作业台账 | ST-05 的天平 |
| 设备或调度系统有自己的 REST API（AGV 车队、带网页接口的仪器） | `rest_map_v1` | 驱动作业台账 + 设备返回的任务号 | AGV-01 / AGV-02 |
| 厂家调度软件 / MES / 集成商服务经数据库中间表对接（中间库） | `sql_table_v1` | 中间库（作业表主键是指令号） | ST-01-B 高通量匀浆站 B |
| 一个工位由几台接口不同的仪器组成 | `composite_v1` | 各子驱动 | ST-05 真空干燥与称重站 |
| 检测软件只能自动导出结果文件（CSV、键值表），不接受外部启动 | 结果文件接收器（`connectors/result_files`） | 按文件内容摘要去重 | — |

「设备侧」的四个驱动要求设备（或网关）认识 ILCS 指令号：按指令号去重、按指令号查询。现场设备大多做不到——
这时用映射驱动，由驱动自己的作业台账补上这一层（见下文「设备不认识 ILCS 指令号：驱动作业台账」），
**但设备只接受 ILCS 这一个上位机下发作业**这一前提要在现场确认。

## 通用结构

```json
{
  "kind": "real",
  "driver": "modbus_tcp_v1",
  "protocol": "Modbus TCP",
  "version": "vendor-profile-1.0",
  "enabled": true,
  "config": {
    "host": "10.20.1.31",
    "port": 502,
    "unit_id": 1,
    "connect_timeout_sec": 3,
    "request_timeout_sec": 5,
    "capabilities": {"cap.mix": 1},
    "params": {"temp": 1, "rpm": 2}
  },
  "credential_ref": "",
  "supports_hold": true,
  "supports_abort": true,
  "supports_query": true,
  "supports_dedup": true,
  "note": "涂布站 3 号线；PLC 程序版本 P-2026.09"
}
```

`config` 会进入审计和备份，禁止出现 `password`、`secret`、`token`、`api_key`、`private_key` 等秘密原文。秘密只保存 `vault://`、`env://` 或 `file://` 引用，运行环境负责解析。

## 已内置：Modbus TCP 驱动（modbus_tcp_v1）

设备（PLC 程序或协议网关）实现 `contracts/modbus/TaskRegisters.json` 的任务寄存器契约：保持寄存器分成身份区、
指令邮箱、应答区、查询选择、查询结果五块，多字节数值一律大端字节序、大端字序，指令号按 40 字符 ASCII 存放。
握手固定为「整块写邮箱 → 单独写触发序号 → 轮询应答序号」，设备写应答时**最后**写序号。

```json
{
  "kind": "real",
  "driver": "modbus_tcp_v1",
  "protocol": "Modbus TCP",
  "config": {
    "host": "modbus-sim-mixer",
    "port": 5020,
    "unit_id": 1,
    "base_address": 0,
    "expected_device_id": "SIM-MIX-01",
    "connect_timeout_sec": 3,
    "request_timeout_sec": 10,
    "poll_interval_ms": 50,
    "heartbeat_stale_sec": 30,
    "probe_interval_sec": 10,
    "capabilities": {"cap.degas": 1, "cap.dose_liquid": 2, "cap.dose_solid": 3, "cap.mix": 4},
    "params": {"mass": 1, "rate": 2, "rpm": 3, "temp": 4, "vacuum": 5, "volume": 6},
    "material_map": {"volume": {"material": "NMP 溶剂", "unit": "mL", "factor": 1}}
  },
  "supports_hold": true, "supports_abort": true, "supports_query": true, "supports_dedup": true
}
```

- `capabilities`：能力 → 能力码（1–65535）；`params`：参数名 → 参数槽位（1–16，float32）。PLC 不认 ILCS 的参数名，
  这两张表必须与设备方逐项核对。没有映射的能力或参数、以及孔位矩阵这类结构化参数，驱动直接拒绝，**不写触发**。
- 设备按槽位回报实测值，驱动再按 `params` 换回参数名放进 `delivered` 与遥测；`material_map` 把某个实测参数折算成
  `delivered.materials`，系统据此入库存。
- 应答码 1–4（参数非法 / 联锁 / 忙 / 不支持）与 Modbus 异常应答是明确失败；写了触发却在 `request_timeout_sec` 内
  等不到应答序号是结果未知，驱动绝不重写触发。驱动重启后从设备当前的触发与应答序号里较大的一个接着编号。
- 在线状态由执行器探测（读身份区）。身份区的心跳计数超过 `heartbeat_stale_sec` 不变，按 PLC 程序停止判失联。
- 标准 Modbus TCP 没有加密与认证：只能放在隔离的控制网段，`host` 必须列入白名单；需要加密时由网关转成 OPC UA 或 HTTPS。
- 设备身份标志位里 `simulator` 置位的设备在正式环境被拒绝接入。

## 已内置：OPC UA 驱动（opcua_v1）

设备（或厂商 OPC UA 服务器）实现 `contracts/opcua/TaskExecution.json`：命名空间 `urn:ilcs:task-execution` 下
`Objects/ILCS/TaskExecution` 对象上的 `SubmitTask` / `QueryTask` / `HoldTask` / `AbortTask` 方法（入参、出参都是
String）与 `DeviceIdentity` 变量。回执 JSON 与 HTTPS JSON 契约一致，孔位矩阵参数原样传递。

```json
{
  "kind": "real",
  "driver": "opcua_v1",
  "protocol": "OPC UA",
  "credential_ref": "file:///run/secrets/ilcs/opcua/ilcs-client.json",
  "config": {
    "endpoint": "opc.tcp://opcua-sim-calender:4840/ilcs/",
    "security_policy": "Basic256Sha256",
    "security_mode": "SignAndEncrypt",
    "server_certificate": "/run/secrets/ilcs/opcua/SIM-CAL-01.crt",
    "application_uri": "urn:ilcs:client",
    "expected_device_id": "SIM-CAL-01",
    "connect_timeout_sec": 3,
    "request_timeout_sec": 10,
    "probe_interval_sec": 10
  },
  "supports_hold": true, "supports_abort": true, "supports_query": true, "supports_dedup": true
}
```

- `server_certificate` 钉住服务器证书（PEM 或 DER），不信任首次连接时拿到的证书；必须位于 `ILCS_ADAPTER_CREDENTIAL_ROOT` 内。
- `credential_ref` 指向客户端证书描述文件 `{"certificate": "...", "private_key": "..."}`（相对路径按描述文件所在目录）。
  客户端证书的 SAN 里要有 `application_uri`，并提前加入服务器的信任列表。
- 拒绝状态码：`BadInvalidArgument`（参数非法）、`BadInvalidState`（联锁）、`BadResourceUnavailable`（忙）、
  `BadNotSupported`（不支持）为明确失败；会话 / 通道断开、超时为结果未知并重建会话；其他 Bad 状态码按结果未知处理。
- `security_policy: "None"` 只允许非正式环境；上线前记录服务器证书指纹并验证时间同步。

## SiLA 2 / gRPC 示例

```json
{
  "endpoint": "dns:///st-07.lab.local:50051",
  "tls": true,
  "server_name": "st-07.lab.local",
  "connect_timeout_sec": 5,
  "command_timeout_sec": 3600,
  "feature_map": {
    "cap.test": "org.sila2.examples.electrochemistry.RunTest",
    "hold": "org.sila2.core.commands.Pause",
    "abort": "org.sila2.core.commands.Cancel"
  }
}
```

必须固定实际使用的 Feature Identifier、命令参数/响应版本和取消语义。长任务超时指“状态查询失败”还是“设备动作失败”要分别定义。

## 已内置：HTTPS JSON 网关驱动

驱动键 `http_json_v1`。厂商 SDK、PLC 或私有协议可由现场网关
转换成这组 HTTP 端点，不需要把厂商判断写进业务服务。正式环境只允许 HTTPS，且
`base_url` 的主机必须列入 `ILCS_ADAPTER_ALLOWED_HOSTS`。

```json
{
  "kind": "real",
  "driver": "http_json_v1",
  "protocol": "HTTPS JSON",
  "version": "1.0",
  "credential_ref": "file:///run/secrets/ilcs/ST-07.json",
  "config": {
  "base_url": "https://instrument-gateway.lab.local/api/v1",
  "verify_tls": true,
  "connect_timeout_sec": 3,
  "request_timeout_sec": 10,
  "device_timezone": "Asia/Shanghai",
  "ca_file": "/run/secrets/ilcs/lab-gateway-ca.pem",
  "expected_device_id": "ST-07",
  "paths": {
    "submit": "/commands",
    "query": "/commands/{command_id}",
    "hold": "/commands/{command_id}/hold",
    "abort": "/commands/{command_id}/abort",
    "health": "/health"
  },
  "idempotency_header": "Idempotency-Key"
  },
  "supports_hold": true,
  "supports_abort": true,
  "supports_query": true,
  "supports_dedup": true
}
```

网关 `/health` 可以同时回报 `interlock`、`accepts_commands`、`simulator`：配了 `"heartbeat_mode": "probe"` 时执行器按
`probe_interval_sec` 读 `/health` 判在线并同步联锁；`simulator: true` 的网关在正式环境被拒绝接入。

凭据文件只能位于 `ILCS_ADAPTER_CREDENTIAL_ROOT`（Compose 默认
`/run/secrets/ilcs`），内容可以是纯 token，也可以是：

```json
{"headers":{"Authorization":"Bearer ...","X-Device-Key":"..."}}
```

连接参数的实际语义：

- `connect_timeout_sec` 只约束 TCP 连接与 TLS 握手，`request_timeout_sec` 约束连接建立后的读写。
- `device_timezone` 用于解释**不带偏移**的 `device_ts`，缺省按 UTC；带偏移的时间按偏移换算，
  库内一律存无时区 UTC。
- `ca_file` 为可选的私有 CA 证书，必须位于 `ILCS_ADAPTER_CREDENTIAL_ROOT` 内；不填用系统信任链。
- 驱动**不跟随重定向**，也不读取 `HTTP(S)_PROXY` 环境变量：30x 会被当作明确失败，避免带凭据的
  请求被引到白名单之外或从 HTTPS 降级。

命令提交体包含 `command_id`、`station_id`、`capability`、`params`、`type`、
`batch_id`、`step_index`、`step_id` 与 `target_command_id`。保持 / 终止请求的
`target_command_id` 是它要停止的那条在途动作指令；动作指令本身该字段为空。网关响应必须包含同一 `command_id`、
`state`（`accepted/running/done/failed/unknown`）、ISO-8601 `device_ts` 和
`quality`（`good/bad/uncertain`）。可选的真实遥测格式如下；真实设备不回传时系统保持
“无数据”，不会拿设定值合成曲线冒充实测：

```json
{
  "command_id": "CMD-...",
  "state": "done",
  "device_ts": "2026-09-22T10:20:30Z",
  "quality": "good",
  "delivered": {"speed": 120},
  "telemetry": [{"metric": "actual_speed", "value": 119.8, "setpoint": 120}]
}
```

长任务可以先返回 `accepted` 或 `running`；执行器后续用原 `command_id` 轮询，终态为
`done` 才写检查点并推进。网络超时保留运行态继续查询，不会盲目重发。

响应的判定规则（网关实现必须按此返回，否则会被判成错误的一类）：

| 网关响应 | 系统结论 | 后果 |
|---|---|---|
| 2xx 且回执字段合规 | 按 `state` 处理 | — |
| 2xx 但不是 JSON、`command_id` 不符、字段缺失或取值非法 | **结果未知** | 批次故障，转人工核查，禁止盲目重试 |
| 408 / 409 / 425 / 429 | **结果未知** | 同上；重复投递冲突尤其不能当作「设备没动」 |
| 5xx、连接失败、超时 | **结果未知** | 同上 |
| 30x | 明确失败 | 驱动不跟随重定向 |
| 其他 4xx（400/401/403/404/422 …） | 明确失败 | 网关必须保证返回这些码时设备**确实没有动作** |

不支持查询的设备应通过服务身份调用 `POST /api/runtime/commands/{command_id}/events`
回报 `accepted / done / failed`：系统据此写检查点、结束指令并推进，重复回执只回放原结论；
指令还没交给设备时回执会被 409 拒绝。设备卡死时，执行器按步骤预计时长判超时（先报警，
超过硬上限转结果未知）；长时间步骤请在能力恢复规则里声明 `maxRunMin` 作为硬上限。

**实际消耗**：设备在回执（`done`）的 `delivered.materials` 里报告真实投料量，系统据此入库存：

```json
{"delivered": {"materials": [{"material": "电解液 LP57", "quantity": 0.48, "unit": "mL"}]}}
```

可以用 `lot_id` 代替 `material` 指定批号。超出本批次预留、对不上预留或单位无法换算时不入账并报警。

**矩阵参数**：方案因子声明了作用参数时，动作指令的 `params.wells` 是 `{孔位: {参数: 值}}`，
设备须按孔位执行；步骤里的其他固定参数是所有孔位的缺省值。

**遥测**：`POST /api/runtime/stations/{station_id}/telemetry`，体为
`{"event_id": "...", "command_id": "可选", "points": [{"metric", "value", "setpoint", "device_ts", "quality"}]}`。
同一 `event_id` 重发只入库一次；单次最多 1000 点；`device_ts` 超前服务器 5 分钟以上整批拒收。

SDK 适配器也使用同一契约。SDK 调用必须放在驱动层，不允许在业务服务里按厂商写 `if/else`。

## 已内置：SiLA 2 驱动（sila2_v1）

设备或厂商网关实现 `contracts/sila2/TaskExecution.sila.xml`（`SubmitTask` / `QueryTask` / `HoldTask` /
`AbortTask` 与 `DeviceIdentity` 属性），回执 JSON 与上面的 HTTPS JSON 契约一致。

```json
{
  "kind": "real",
  "driver": "sila2_v1",
  "protocol": "SiLA 2",
  "config": {
    "host": "sila-sim-lh",
    "port": 50052,
    "ca_file": "/run/secrets/ilcs/sila/SIM-LH-01.crt",
    "expected_device_id": "SIM-LH-01",
    "connect_timeout_sec": 3,
    "request_timeout_sec": 10,
    "probe_interval_sec": 10,
    "device_timezone": "UTC"
  },
  "supports_hold": true, "supports_abort": true, "supports_query": true, "supports_dedup": true
}
```

- 在线状态由执行器主动探测（`heartbeat_mode` 默认 `probe`），设备不用推心跳；设备身份里的
  `interlock`、`accepts_commands` 同步为工位联锁与是否接受指令。
- `insecure: true` 只允许在非正式环境使用；正式环境必须 TLS，并用 `ca_file` 指向设备证书的 CA。
- 设备身份里 `simulator: true` 的设备在正式环境被拒绝接入。
- 真机到位前可用 `simulators/` 下的外部模拟设备联调（每种驱动都有），含断连、回执丢失、卡死等故障注入。

## 设备不认识 ILCS 指令号：驱动作业台账

`opcua_map_v1`、`modbus_map_v1`、`line_command_v1`、`mt_sics_v1`、`rest_map_v1` 共用一套作业逻辑（`api/app/adapters/jobs.py`）：

- 每台设备一份台账 `ILCS_ADAPTER_STATE_ROOT/<工位>.json`（缺省是 `ILCS_FILE_ROOT` 的上一级 `/adapter-state`，
  Compose 里即 `/data/adapter-state`，**必须在持久卷上**）。**先落盘再动设备**：执行器任何时刻重启都知道这条指令
  可能已经发给设备，之后按原指令号回答查询；同一指令号重复投递回放原作业，不会让设备再动一次。台账损坏时驱动拒绝工作，
  不当成空台账继续。
- 同一时刻只有一个在途作业。设备在运行 / 保持就明确拒绝（DeviceBusy）；停在上一个作业的完成 / 故障状态时先发复位
  （`acknowledge`），复位不了也拒绝。
- 结论看设备状态：见到运行后回到空闲或报完成 → 完成，并读实测值写进回执与遥测（设定值取指令参数里的同名数值）；
  报故障 → 失败（带故障代码对应的说明）；启动命令回了确认、却一直没见到运行也没有完成信号，超过 `start_timeout_sec`
  （缺省 30 s）→ **结果未知**，转人工核查。设备明确说「排队中」（REST 映射的 `accepted` 状态）时不按启动超时算。
- 启动命令之前的失败（参数写不进、回复报错、没回复）设备没有动作 → 明确失败；启动命令本身被拒 → 明确失败；
  启动命令发出后没拿到确认 → 台账记「未确认」、回执结果未知；之后见到设备在运行才按运行处理，质量标 `uncertain`。
- 指令参数必须每个都有对应的写入点或命令模板，否则明确拒绝（不静默丢弃设定值）；孔位矩阵这类结构化参数这些驱动不接，
  请改用 SiLA 2 / OPC UA TaskExecution / HTTPS 网关。
- `material_map`（`{实测参数: {material, unit, factor}}`）把实测值折算成 `delivered.materials`，系统据此入库存。
- 设备身份里（厂商、型号、序列号、固件任一字段）带 `ILCS-SIMULATOR` 的是模拟设备，正式环境拒绝接入。

## 已内置：OPC UA 节点映射（opcua_map_v1）与 Modbus 点表映射（modbus_map_v1）

两种驱动共用一份点表映射（`api/app/adapters/point_map.py`），先登记点、再用点名描述每项能力：

```json
{
  "endpoint": "opc.tcp://plc-sim-coater:4841/plc/",
  "security_policy": "Basic256Sha256", "security_mode": "SignAndEncrypt",
  "server_certificate": "/run/secrets/ilcs/opcua/SIM-COAT-01.crt", "application_uri": "urn:ilcs:client",
  "points": {
    "state": "nsu=urn:ilcs:sim:plc;s=Coater.State", "error": "nsu=urn:ilcs:sim:plc;s=Coater.ErrorCode",
    "cmd_start": "nsu=urn:ilcs:sim:plc;s=Coater.CmdStart", "sp_temp": "nsu=urn:ilcs:sim:plc;s=Coater.SP_temp",
    "pv_temp": "nsu=urn:ilcs:sim:plc;s=Coater.PV_temp", "job_id": "…JobId", "job_latched": "…JobLatched", "…": "…"
  },
  "identity": {"device_id": "serial", "model": "model", "vendor": "vendor", "firmware": "firmware"},
  "ready": {"point": "remote", "ok": [true]}, "interlock": {"point": "safety", "ok": [true]},
  "heartbeat": {"point": "heartbeat", "stale_sec": 30},
  "job_id": {"write": "job_id", "echo": "job_latched"},
  "capabilities": {"cap.coat": {
    "constants": {"operation": 1},
    "recipe": {"point": "recipe", "map": {"COAT-STD": 1, "COAT-180": 12}, "default": "COAT-STD"},
    "write": {"thickness": "sp_thickness", "temp": "sp_temp"},
    "start": {"point": "cmd_start", "value": true, "pulse_ms": 300},
    "actuals": {"thickness": "pv_thickness", "temp": "pv_temp"}}},
  "status": {"point": "state", "states": {"0": "idle", "1": "running", "2": "held", "3": "done", "4": "failed"}},
  "error": {"point": "error", "codes": {"17": "过程报警", "31": "程序号不存在"}},
  "hold": {"point": "cmd_hold", "value": true, "pulse_ms": 300},
  "resume": {"…": "…"}, "abort": {"…": "…"}, "acknowledge": {"…": "…"}
}
```

- 下发顺序：就绪 / 联锁检查 → 常量 → 程序号（`recipe.map` 把设备方法的设备端程序换成 PLC 程序号，查不到就拒绝）→
  设定值 → 指令号（`job_id.write`）→ 启动信号。启动信号之前任何一次写入失败都说明设备没动。
- `job_id.echo`：PLC 在启动时把指令号锁存到这个点。启动信号没拿到确认的作业，执行器重启后按回显确认「确实是这条在跑」。
- 心跳点超过 `stale_sec` 不变按 PLC 程序停止判失联（变量还能读不等于程序在跑）。
- OPC UA：节点 ID 用 `ns=3;s=…` 或带命名空间 URI 的 `nsu=<URI>;s=…`（服务器重启后序号可能变，URI 不变）；
  写入按节点当前的数据类型编码；启动也可以是方法调用 `"start": {"method": {"object": …, "method": …, "args": ["{program}"]}}`，
  方法返回 `BadInvalidState` 等约定状态码是明确拒绝。安全与证书同 `opcua_v1`。
- Modbus：点写成 `{"table": "holding|input|coil|discrete", "address": 0 基地址, "type": "uint16|int16|uint32|int32|float32|bool|ascii", "scale": 0.1, "word_order": "big|little", "bit": 0}`；
  只有 holding 与 coil 可写，保持寄存器里的位只读。标准 Modbus TCP 没有加密与认证：只能放在隔离的控制网段。

## 已内置：串口 / TCP 命令驱动（line_command_v1）

面向「厂家给了一份命令手册」的仪器。命令、回复解析与状态映射全在配置里（ST-05 干燥箱的完整例子见预设文件）：

```json
{
  "transport": {"kind": "serial", "port": "rfc2217://moxa-01.lab.internal:4001", "baudrate": 9600, "parity": "N"},
  "write_terminator": "\r\n", "read_terminator": "\r\n", "request_timeout_sec": 3,
  "identity": {"send": "*IDN?", "pattern": "^(?P<vendor>[^,]*),(?P<model>[^,]*),(?P<device_id>[^,]*),(?P<firmware>.*)$"},
  "ready": {"send": "REM?", "pattern": "^(?P<value>\\w+)$", "ok": ["REMOTE"]},
  "interlock": {"send": "DOOR?", "pattern": "^(?P<value>\\w+)$", "ok": ["CLOSED"]},
  "error_pattern": "^ERR",
  "capabilities": {"cap.vacuum_dry": {"program": "VD-120", "start": [
    {"send": "PROG {program}", "expect": "^OK$"}, {"send": "SP {temp:.1f}", "expect": "^OK$"},
    {"send": "VAC {vacuum:.2f}", "expect": "^OK$"}, {"send": "RUN", "expect": "^OK$"}]}},
  "status": {"send": "STAT?", "pattern": "^(?P<state>[A-Z]+)(,(?P<detail>.*))?$",
             "states": {"IDLE": "idle", "RUN": "running", "HOLD": "held", "DONE": "done", "ALARM": "failed"}},
  "error_codes": {"E05": "干燥过程报警：温度偏差超限"},
  "actuals": [{"send": "PV?", "pattern": "^(?P<temp>[-\\d.]+),(?P<vacuum>[-\\d.]+)$"}],
  "hold": [{"send": "HOLD", "expect": "^OK$"}], "resume": [{"send": "CONT", "expect": "^OK$"}],
  "abort": [{"send": "STOP", "expect": "^OK$"}], "acknowledge": [{"send": "ACK", "expect": "^OK$"}]
}
```

- 通道：`{"kind": "tcp", "host", "port"}`，或 `{"kind": "serial", "port": …}`——本机串口只允许 `/dev/tty*`、
  `/dev/serial/by-id/*`、`COMn`；串口服务器用 `rfc2217://` 或 `socket://`，主机要在白名单。缺省每次操作开一次会话
  （不长期占着串口），`keep_open: true` 可保持连接；`greeting` 匹配连接后设备先发的欢迎语。
- 启动命令列表里 `motion: true` 的那条（缺省最后一条）才让设备动作；它之前的命令被拒、没回复都算设备没动。
- 模板 `{参数:格式}` 只允许按名字取值，值里有控制字符直接拒绝；`{program}` 是设备方法的设备端程序（缺省取能力的 `program`）。
- `idle_after_start: "done"`：设备没有「运行中」可查、回到空闲就代表做完时才打开（缺省空闲而没见过运行按结果未知）。
- UR 机械臂仪表盘服务（TCP 29999）的映射见预设 ARM-01：`load <程序>.urp` + `play` 启动，`programState` 查状态，
  `safetystatus` 作联锁、`robotmode` 作就绪。

## 已内置：MT-SICS 天平驱动（mt_sics_v1）

梅特勒天平的 MT-SICS 通用命令（RS232 或以太网 TCP，CR LF）：`I2` / `I3` / `I4` / `I10` 读型号、软件版本、序列号、天平编号，
`S` 稳定称重、`SI` 立即读数、`T` 去皮、`Z` 置零、`@` 复位（终止）。

```json
{"transport": {"kind": "tcp", "host": "balance-01.lab.internal", "port": 4305}, "request_timeout_sec": 3,
 "expected_device_id": "B123456789", "device_id_source": "serial",
 "capabilities": {"cap.weigh": {"action": "weigh", "result": "mass", "unit": "g", "stable_timeout_sec": 15,
                                "zero_first": false, "tare_first": false}}}
```

- 称重是即时动作：读数到手作业就完成，`delivered` 带重量、单位、是否稳定与原始读数；指令里的同名参数（如期望单片质量）
  只作遥测设定值，不下发给天平。重投同一指令号回放原读数，不再称第二次。
- `S I`（不稳定或正忙）、`S +` / `S -`（超载 / 欠载）、`ES` / `ET` / `EL` 是明确失败；发出 `S` 后没回复是结果未知。
- 型号的扩展功能（自动加料头、方法库）不在 MT-SICS 通用命令里：确认厂家命令或网页服务接口后，用 `line_command_v1`
  / `rest_map_v1` 映射，或经厂家 SDK 接口服务接入。

## 已内置：REST 接口映射（rest_map_v1）

设备或调度系统有自己的 REST API 时用。每项能力一个请求模板，驱动把设备返回的任务号记进作业台账：

```json
{
  "base_url": "https://mir-01.lab.internal/api/v2.0.0",
  "headers": {"Accept-Language": "en_US"},
  "identity": {"method": "GET", "path": "/status",
               "fields": {"device_id": "robot_name", "model": "model", "firmware": "software_version"},
               "interlock": {"field": "state_text", "values": ["EmergencyStop", "Error"]}},
  "capabilities": {"cap.transfer": {"method": "POST", "path": "/mission_queue", "handle": "id",
    "body": {"mission_id": "{mission}", "message": "ILCS {command_id}",
             "parameters": [{"id": "From", "value": "{from_position}"}, {"id": "To", "value": "{to_position}"}]},
    "defaults": {"mission": "<任务模板 GUID>"}}},
  "positions": {"HOTEL-01/S01": "<站点 GUID>", "ST-05/N1": "<站点 GUID>"},
  "status": {"method": "GET", "path": "/mission_queue/{handle}", "field": "state", "error_field": "message",
             "states": {"Pending": "accepted", "Executing": "running", "Paused": "held", "Done": "done", "Aborted": "failed"}},
  "lookup": {"method": "GET", "path": "/mission_queue", "detail_path": "/mission_queue/{id}", "id_field": "id",
             "match_field": "message", "match": "ILCS {command_id}", "recent": 20},
  "hold": {"method": "PUT", "path": "/status", "body": {"state_id": 4}},
  "resume": {"method": "PUT", "path": "/status", "body": {"state_id": 3}},
  "abort": {"method": "DELETE", "path": "/mission_queue/{handle}"}
}
```

- 身份请求必填（没有它就无法判断在线）；`busy` 可选，调度系统自己排队时不配。
- 转运指令的 `{from.location_id}` / `{to.location_id}` 可以直接用；配置了 `positions` 时 `{from_position}` / `{to_position}`
  按 ILCS 位置编号查表，查不到明确拒绝——不把 ILCS 编号猜成车队站点。没配 `positions` 就原样传 ILCS 编号。
- 请求体里带上 ILCS 指令号并配置 `lookup`：启动请求没拿到应答的作业，下一次查询时在设备队列里按指令号找回。
- HTTP 分类、TLS、代理与重定向策略、凭据引用与 `http_json_v1` 相同；MiR 的 Basic 认证头写进凭据文件
  `{"headers": {"Authorization": "Basic …"}}`，不写进配置。上面的 MiR 字段按 MiR REST API 2.x 写，接实机前按现场版本核对。

## 已内置：数据库中间表（sql_table_v1）

中间库是厂家调度软件、MES、集成商服务常见的对接方式：ILCS 往作业表插一行（`state = 'new'`），设备侧轮询作业表、
执行后回写状态与结果，并在设备表里维持心跳。表结构与约定见 `contracts/sql/ilcs_exchange.sql`。

```json
{"url": "postgresql+psycopg2://ilcs_exchange@exchange-db.lab.internal:5432/exchange",
 "jobs_table": "ilcs_jobs", "device_table": "ilcs_device", "device_id": "SLR-B-01",
 "heartbeat_stale_sec": 30, "request_timeout_sec": 10, "connect_timeout_sec": 3}
```

- 作业表主键是 ILCS 指令号：重投只撞主键、回放原结论；设备侧**只按主键去重**。执行器重启后按指令号查回。
- 状态：`new` / `accepted` 已接受，`running` / `held` 执行中，`done` 完成，`failed` / `aborted` 失败，`rejected` 设备明确没动作（带原因）。
- 保持 / 终止写一行 `task_type = hold / abort` 的作业，设备侧在 `request_timeout_sec` 内改成 done 才算确认，否则结果未知。
- 健康检查读设备表：`heartbeat_at` 超过 `heartbeat_stale_sec` 不变判失联；`methods_json` 是设备自报的程序目录。
- 口令不写进 `url`：`credential_ref`（env:// 或 file://）给口令。PostgreSQL 直接可用；SQL Server 需在镜像里装 pyodbc
  与 ODBC 驱动，MySQL 需装 pymysql；SQLite 只用于非正式环境。ILCS 的数据库账号只需作业表 SELECT / INSERT、设备表 SELECT。

## 已内置：组合工位（composite_v1）

一个工位由几台接口不同的仪器组成时用（例：真空干燥箱走串口命令 + 天平走 MT-SICS）：

```json
{"probe_interval_sec": 10, "routes": [
  {"name": "oven", "capabilities": ["cap.vacuum_dry"], "driver": "line_command_v1", "config": {"…": "…"}},
  {"name": "balance", "capabilities": ["cap.weigh"], "driver": "mt_sics_v1", "config": {"…": "…"}, "credential_ref": ""}]}
```

每项能力只能落在一条路由上；路由里是任意已登记的真实驱动（不能再嵌套组合），各自校验配置、各自一份台账
（`<工位>#<路由名>`）。健康检查要每台仪器都在线；任一台联锁即联锁。回执来源标子驱动（如 `real:mt_sics_v1`）。

## 厂家 SDK 接口服务（只有 Windows SDK / DLL 的设备）

在设备旁的工控机上跑一个小服务：调用厂家 SDK，对 ILCS 提供上文「HTTPS JSON 网关驱动」的契约，ILCS 侧用
`http_json_v1`。服务要自己保证三件事：**按 ILCS 指令号去重**（重复的 `POST /commands` 回放原结论）、**按指令号查询**
（执行器重启后要能问到）、**回执丢失时宁可不回也不编造**（驱动按结果未知处理）。可以直接照 `simulators/http_gateway/server.py`
的路由与状态码实现，把其中的模拟设备换成 SDK 调用。ST-07 充放电柜的预设就是这种接法。

## 驱动必须实现的契约

每个真实驱动至少实现：

1. `healthcheck()`：验证配置、凭据可读取、网络可达、设备身份/序列号符合预期；失败抛异常。
2. `submit(request)`：携带系统生成的 `command_id`，只在设备明确接受后返回 `accepted/running/done`。
3. `query(command_id)`：按原指令查询；不支持时明确返回不支持并关闭能力声明。
4. `hold(request)` / `abort(request)`：只有设备真实支持时才声明为 `true`。
5. 回执包含原 `command_id`、设备时间、质量标记、实际下发参数；遥测注明来源。

网络无响应是 `AdapterUnreachable`（结果未知），设备明确拒绝才是 `AdapterError`（确定失败）。两者不能混用。
设备有响应但无法据此确认结果（重复投递冲突、限流、回执不合规）用 `AdapterIndeterminate`，
它是 `AdapterUnreachable` 的子类，按结果未知处理。驱动内部抛出的其他意外异常同样按结果未知处理。

### 设备方法目录（驱动自报）

「工位配置」适配器配置里的「读取设备方法目录」调用 `POST /api/stations/{id}/adapter/describe`，读驱动的设备身份：

- HTTPS 网关的 `/health`、SiLA 2 的 `DeviceIdentity`、OPC UA 的 `DeviceIdentity` 节点返回的 JSON 里带
  `vendor`、`firmware`、`model`、`methods`（`[{program, name, capability}]`）、`commands` 就按设备自报；
- Modbus 寄存器布局带不了目录，在连接配置 JSON 里登记 `"methods": ["VD-120", "VD-90"]`（或对象列表），
  来源标为「按登记配置」；`vendor`、`firmware` 同样可以写在配置里。
- `program` 为 `*` 表示接受任意设备端程序（模拟器默认这样报）。

流程步骤引用设备方法时，方法的设备端程序不在目录里的工位不承接这一步；从没读过目录（空）的工位不据此排除。
设备自报的型号与工位关联资产在「仪器设备」登记的型号核对（没有资产档案的工位与工位登记的型号核对），不一致只提示、不覆盖登记值——设备方法的适用型号按登记值匹配。
设备动作指令带 `method: {id, code, version, name, program}`：HTTPS 网关在请求体里、SiLA 2 / OPC UA 在
`ContextJson` / 上下文 JSON 里，驱动按 `program` 选设备上的程序。Modbus 仍按能力码下发，程序由 PLC 侧配置保证。

正式环境（`ILCS_ENVIRONMENT=production`）禁止模拟适配器执行任何指令，也不允许模拟心跳：
未配置真实驱动的工位在下发时被拒（`simulation_adapter`），执行器投递时也会拒绝。

## 上线核对清单

- [ ] 设备静态 IP/DNS、端口、VLAN、防火墙和 NTP 已确认
- [ ] 资产序列号与系统工位绑定一致
- [ ] 凭据仅存于密钥管理器，具备最小权限和轮换方案
- [ ] 参数单位、上下限、精度、字节序/编码与设备文件一致
- [ ] `command_id` 去重、重复投递、查询、超时和断线恢复经过实机测试
- [ ] 保持/终止的物理副作用和最长保持时间已写入能力恢复规则
- [ ] 心跳降级/失联、公共联锁、执行门关闭均有测试证据
- [ ] 执行器重启后能对账；不能确认时进入人工核查而非自动重试
- [ ] 模拟数据与真实数据来源标记可区分
- [ ] 配置变更已签名，版本递增，旧连接失效，重新健康检查后才上线
