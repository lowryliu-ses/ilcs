# 真实设备适配器配置模板

系统把“协议显示名”“驱动键”“非秘密连接配置”“凭据引用”和“能力声明”分开保存。真实设备必须使用 `kind=real`，且 `driver` 必须对应后端已注册实现；缺少实现时保存、健康检查和重连都会拒绝，绝不回落到模拟器。

## 接法：改配置、套模板、写设备模块、放进驱动宿主

ILCS 只经两个契约接设备：`sila2_v1`（SiLA 2 设备服务）与 `http_json_v1`（HTTPS 网关），外加内置模拟。协议驱动都在 ILCS
进程之外。

| 情况 | 怎么做 | 要不要重启 |
|---|---|---|
| 设备给的是串口 / TCP 文本命令、Modbus 点表、OPC UA 节点、REST，或 PLC / OPC UA 服务器按 ILCS 任务契约编程 | 在驱动宿主（`ilcs-devices/host/README.md`）登记设备文件（插件配置见 `ilcs-devices/host/插件配置.md`），ILCS 工位用 `sila2_v1` 连驱动宿主；改点表、改映射只发布驱动宿主，ILCS 检出驱动配置摘要变了就停派工、要求签名批准与重新验收 | ILCS 不用；驱动宿主重启 |
| 厂家只给 SDK / DLL、私有协议、逻辑复杂 | 按 `ilcs-devices/gateway/README.md` 写一个**设备模块**：基于 `ilcs-devices/gateway/ilcs_gateway` 起一个独立网关，ILCS 侧用 `http_json_v1` 接入；模块自带模拟接口与测试，交付 `profile.json`（ILCS 的设备接入模板） | ILCS 不用；网关升级只重启网关自己 |
| 设备自己就是实现了 ILCS 特性的 SiLA 2 服务器 | ILCS 工位直接用 `sila2_v1` 连它 | 不用 |
| 新协议 | 写成驱动宿主的插件（`ilcs-devices/host/ilcs_host/plugins`，同一套作业台账与测试辅助），不进 ILCS 进程 | ILCS 不用；驱动宿主重建、重启 |

同一类设备有好几台时，ILCS 这边的连接配置（网关地址形式、证书、验收缺省）可以存成**设备接入模板**（「工位与接入 → 接入模板」），
工位套用模板、只填自己的连接参数；签名保存后下一轮执行器就用新配置，不用重启。

不支持从页面上传驱动代码、在执行器里热加载：执行器是单活进程、握着全站的在途指令，插件出一次错就是全站停；
Python 热重载不可靠；上传代码绕开代码评审，审计答不出「这条指令是哪一版驱动执行的」。

「设备连接」的手工配置和「接入模板」都按驱动目录出表单（`adapters/catalog.py` 里 `sila2_v1`、`http_json_v1` 的每个配置项连同
嵌套结构一起登记：接口路径、模拟设备控制口、环境采集、验收缺省、方法目录）。表单编辑不了的写法原样保留、就地按 JSON 改，
完整 JSON 随时可以切过去直接改；内置模拟没有配置项说明，只按 JSON 写。

保存前系统按驱动检查配置（`adapters/catalog.py`：必填项、类型，再构造一次驱动实例但不连设备），配错了当场拒绝并逐条列出；
拼错的键（顶层和嵌套结构里的，比如 `paths.helth`）只提醒（驱动会忽略它）。「设备连接」配置里的「检查配置」按钮做同样的检查、不保存。

登记工位时没接设备的（没填协议），在「工位与接入 → 设备连接」里点「接入设备」补接：同样可以套模板或手工配置，检查与登记新工位时一起建的同一套（`POST /api/stations/{id}/adapter`），接入后按新设备欠一份接入验收。

**设备上还有可能在动作的指令时**（在途、已保持、结果未知），只能改说明、停用、超时与探测周期；换驱动、换连接目标、改状态映射
会被拒绝——新驱动实例查不回原指令，换了设备服务还可能按另一套状态码判结论。等指令结束，或保持 / 终止并现场核查后再改。

**设备主机白名单** `ILCS_ADAPTER_ALLOWED_HOSTS` 可以写主机名、IP、网段与域名后缀：`instrument-gateway.lab.internal,10.20.1.0/24,.lab.internal`。
设备网段、设备域名下新接的设备不用改 `.env`、不用重启；主机名不去解析再比网段。正式环境不许 `*`，IPv4 网段不宽于 /16、IPv6 不宽于 /48，
域名后缀至少两级。经驱动宿主接的设备，ILCS 这边只要列驱动宿主的主机名；设备本身的主机写在驱动宿主 `host.json` 的
`allowed_hosts` 里。

## 先选驱动：设备给的是什么接口

| 设备 / 现场给的接口 | ILCS 驱动 | 设备那一侧 | 示例工位 |
|---|---|---|---|
| 厂家或集成商按 ILCS 网关契约做了 HTTPS 服务；只有 Windows SDK / DLL 的设备由「厂家 SDK 接口服务」包成这份契约 | `http_json_v1`（直连网关），或 `sila2_v1`（经驱动宿主的 `http_json` 插件） | 网关（设备模块）按指令号去重、查询 | ST-07 充放电柜（直连）；天平、IKA、拉曼、冷水机、电化学、Neware 与电解液线的模拟网关（经驱动宿主） |
| SiLA 2 设备服务实现了 ILCS 的特性（厂商网关、只有 TaskExecution 的老服务器） | `sila2_v1` | 设备服务按指令号去重、查询 | ST-01-A、ST-06 |
| PLC / 视觉系统的 OPC UA 节点、Modbus 寄存器表；串口 / TCP 文本命令仪器；设备或调度系统的 REST API；按 ILCS 任务寄存器 / TaskExecution 节点编程的 PLC | `sila2_v1`（接驱动宿主） | 驱动宿主的插件：`opcua_map` / `modbus_map` / `line_command` / `rest_map`（插件的作业台账）、`modbus_task` / `opcua_task`（设备侧）——见 插件配置（`ilcs-devices/host/插件配置.md`） | ST-PF-*（ProtoForge）、ST-OCV-SIM / ST-OCV2-SIM / ST-ACIR-SIM（电芯检测仪表） |
| 检测软件只能自动导出结果文件（CSV、键值表），不接受外部启动 | 结果文件接收器（`ilcs-devices/connectors/result_files`） | 按文件内容摘要去重 | — |

## 通用结构

```json
{
  "kind": "real",
  "driver": "sila2_v1",
  "protocol": "SiLA 2（驱动宿主）",
  "version": "site-local-r3",
  "enabled": true,
  "config": {
    "host": "driver-host",
    "port": 50201,
    "ca_file": "/run/secrets/ilcs/host/driver-host.crt",
    "expected_device_id": "PLC-COAT-03",
    "connect_timeout_sec": 3,
    "request_timeout_sec": 10,
    "probe_interval_sec": 10
  },
  "credential_ref": "file:///run/secrets/ilcs/host/ilcs.token",
  "supports_hold": false,
  "supports_abort": false,
  "supports_query": true,
  "supports_dedup": true,
  "note": "涂布站 3 号线（驱动宿主上的 PLC-COAT-03，modbus_map）；PLC 程序版本 P-2026.09"
}
```

`config` 会进入审计和备份，禁止出现 `password`、`secret`、`token`、`api_key`、`private_key` 等秘密原文。秘密只保存 `vault://`、`env://` 或 `file://` 引用，运行环境负责解析。

## 已内置：HTTPS JSON 网关驱动

驱动键 `http_json_v1`。厂商 SDK、PLC 或私有协议可由现场网关
转换成这组 HTTP 端点，不需要把厂商判断写进业务服务。正式环境只允许 HTTPS，且
`base_url` 的主机必须在 `ILCS_ADAPTER_ALLOWED_HOSTS` 里（主机名、IP、网段或域名后缀）。
网关用 `ilcs-devices/gateway/ilcs_gateway` 写，契约里的去重、台账、查询、回执丢失的处理都已经做好（见「厂家 SDK 接口服务」）。

网关也可以**经驱动宿主接**：驱动宿主的 `http_json` 插件（`ilcs-devices/host/插件配置.md`「ILCS 网关」）把它转成 SiLA 服务，
工位改用 `sila2_v1` 接驱动宿主，和别的设备一起在驱动宿主的设备管理台里看状态、起停、改连接，驱动配置闸门照样生效。
网关照旧在设备旁边跑，回执原样转过来；同一个网关直连与经驱动宿主各跑一遍接入验收清单，结论一样。换过去时：
- 连接配置写驱动宿主的主机、端口与证书；模板里给 ILCS 自己用的键（`wells_per_command`：一条指令最多几个样本）照样写进来；
- 验收的故障项目照做：`simulator_control` 指向网关自己的 API（`{"url": "https://<网关>:8443/api/v1", "ca_file": …,
  "token_ref": …}`）；
- 换驱动后要重新过动作级验收，连上后重读设备自报的方法目录（排程只往报过这个程序的工位排）。
本机的模拟网关用 `scripts/load-driver-host-devices.py register --only <工位> [--acceptance]` 改接；别的登记脚本见到工位已经
经驱动宿主接着就沿用，不改回直连。

```json
{
  "kind": "real",
  "driver": "http_json_v1",
  "protocol": "HTTPS JSON",
  "version": "1.0",
  "credential_ref": "file:///run/secrets/ilcs/ST-07.json",
  "config": {
  "base_url": "https://instrument-gateway.lab.local/api/v1",
  "verify_tls": true,
  "connect_timeout_sec": 3,
  "request_timeout_sec": 10,
  "device_timezone": "Asia/Shanghai",
  "ca_file": "/run/secrets/ilcs/lab-gateway-ca.pem",
  "expected_device_id": "ST-07",
  "paths": {
    "submit": "/commands",
    "query": "/commands/{command_id}",
    "hold": "/commands/{command_id}/hold",
    "abort": "/commands/{command_id}/abort",
    "health": "/health"
  },
  "idempotency_header": "Idempotency-Key"
  },
  "supports_hold": true,
  "supports_abort": true,
  "supports_query": true,
  "supports_dedup": true
}
```

网关 `/health` 可以同时回报 `interlock`、`accepts_commands`、`simulator`：配了 `"heartbeat_mode": "probe"` 时执行器按
`probe_interval_sec` 读 `/health` 判在线并同步联锁；`simulator: true` 的网关在正式环境被拒绝接入。

凭据文件只能位于 `ILCS_ADAPTER_CREDENTIAL_ROOT`（Compose 默认
`/run/secrets/ilcs`），内容可以是纯 token，也可以是：

```json
{"headers":{"Authorization":"Bearer ...","X-Device-Key":"..."}}
```

连接参数的实际语义：

- `connect_timeout_sec` 只约束 TCP 连接与 TLS 握手，`request_timeout_sec` 约束连接建立后的读写。
- `device_timezone` 用于解释**不带偏移**的 `device_ts`，缺省按 UTC；带偏移的时间按偏移换算，
  库内一律存无时区 UTC。
- `ca_file` 为可选的私有 CA 证书，必须位于 `ILCS_ADAPTER_CREDENTIAL_ROOT` 内；不填用系统信任链。
- 驱动**不跟随重定向**，也不读取 `HTTP(S)_PROXY` 环境变量：30x 会被当作明确失败，避免带凭据的
  请求被引到白名单之外或从 HTTPS 降级。

命令提交体包含 `command_id`、`station_id`、`capability`、`params`、`type`、
`batch_id`、`step_index`、`step_id` 与 `target_command_id`；步骤引用了设备方法时带 `method`（`{id, code, version, name, program}`），
投料步骤带 `material`（`{name, unit, param}`：物料名、单位、用量取哪个参数）——称量加料的网关据此核对装在设备上的是不是这种料；
处理样本的设备动作带 `wells`（这条指令处理的孔位列表，设备认的孔位键，与 `params.wells` 同一口径：有逐孔参数就是它的孔位，
没有逐孔参数的检测步骤、整批同一参数的步骤是这一步的处理对象）——设备一次只测一瓶、指令又没拆开时，靠它知道测的是哪一瓶。保持 / 终止请求的
`target_command_id` 是它要停止的那条在途动作指令；动作指令本身该字段为空。网关响应必须包含同一 `command_id`、
`state`（`accepted/running/done/failed/unknown`）、ISO-8601 `device_ts` 和
`quality`（`good/bad/uncertain`）。可选的真实遥测格式如下；真实设备不回传时系统保持
“无数据”，不会拿设定值合成曲线冒充实测：

```json
{
  "command_id": "CMD-...",
  "state": "done",
  "device_ts": "2026-09-22T10:20:30Z",
  "quality": "good",
  "delivered": {"speed": 120},
  "telemetry": [{"metric": "actual_speed", "value": 119.8, "setpoint": 120}]
}
```

逐孔执行（`params.wells`）时，遥测点可以再带 `well`（孔位）与 `device_ts`（这一孔取实测的设备时间，带时区）：系统按孔位把
这个点关联到样本（与 `delivered.wells` 同一口径），按它自己的时间记；不带的按整条回执的 `device_ts` 记。映射驱动（含驱动宿主
里的插件）逐孔执行时自动带上。

长任务可以先返回 `accepted` 或 `running`；执行器后续用原 `command_id` 轮询，终态为
`done` 才写检查点并推进。网络超时保留运行态继续查询，不会盲目重发。

响应的判定规则（网关实现必须按此返回，否则会被判成错误的一类）：

| 网关响应 | 系统结论 | 后果 |
|---|---|---|
| 2xx 且回执字段合规 | 按 `state` 处理 | — |
| 2xx 但不是 JSON、`command_id` 不符、字段缺失或取值非法 | **结果未知** | 批次故障，转人工核查，禁止盲目重试 |
| 408 / 409 / 425 / 429 | **结果未知** | 同上；重复投递冲突尤其不能当作「设备没动」 |
| 5xx、连接失败、超时 | **结果未知** | 同上 |
| 30x | 明确失败 | 驱动不跟随重定向 |
| 其他 4xx（400/401/403/404/422 …） | 明确失败 | 网关必须保证返回这些码时设备**确实没有动作** |

不支持查询的设备应通过服务身份调用 `POST /api/runtime/commands/{command_id}/events`
回报 `accepted / done / failed`：系统据此写检查点、结束指令并推进，重复回执只回放原结论；
指令还没交给设备时回执会被 409 拒绝。设备卡死时，执行器按步骤预计时长判超时（先报警，
超过硬上限转结果未知）；长时间步骤请在能力恢复规则里声明 `maxRunMin` 作为硬上限。

**实际消耗**：设备在回执（`done`）的 `delivered.materials` 里报告真实投料量，系统据此入库存：

```json
{"delivered": {"materials": [{"material": "电解液 LP57", "quantity": 0.48, "unit": "mL"}]}}
```

可以用 `lot_id` 代替 `material` 指定批号。超出本批次预留、对不上预留或单位无法换算时不入账并报警。

**矩阵参数**：方案因子声明了作用参数时，动作指令的 `params.wells` 是 `{孔位: {参数: 值}}`，
设备须按孔位执行；步骤里的其他固定参数是所有孔位的缺省值。

**按瓶拆开下发**（配置 `wells_per_command`）：设备一次只能处理一瓶（秤上一个位置、光谱仪单测量位、一个通道接一个电池）
时填 1（能同时处理几瓶就填几）。一步要做的瓶（孔位）超过它，ILCS 仍记一条指令，但按瓶拆成依次执行的设备指令
`<指令号>/1`、`/2`……：每条的 `params.wells` 与 `wells` 只带这几瓶（没有逐孔参数的检测步骤也带上孔位，参数为空，设备据此知道测的是哪一瓶），
前一条完成才发下一条（现场由搬运 / 上位机把这一瓶放到位）。每瓶做完就按它回报的实际量入账；全部做完按瓶汇总写检查点与检测结果
（`delivered.runs` 列出各条）。哪一瓶失败或结论未知，整步按它的结论走，已做完的瓶照样入账；终止发给正在做的那一瓶，后面的不再下发；
人工确认后重试 / 续跑跳过已经做完的瓶。预计时长与超时按条数放大。不填就一条指令带全部瓶。

**遥测**：`POST /api/runtime/stations/{station_id}/telemetry`，体为
`{"event_id": "...", "command_id": "可选", "points": [{"metric", "value", "setpoint", "device_ts", "quality"}]}`。
同一 `event_id` 重发只入库一次；单次最多 1000 点；`device_ts` 超前服务器 5 分钟以上整批拒收。

SDK 适配器也使用同一契约。SDK 调用必须放在驱动层，不允许在业务服务里按厂商写 `if/else`。

## 已内置：SiLA 2 驱动（sila2_v1）

设备服务实现 `ilcs-devices/contracts/sila2/README.md` 里 ILCS 的特性，驱动按服务报的「已实现特性」取能力：
- `DeviceInfo`：身份、状态、驱动与配置摘要。没有它的老服务器（只有 TaskExecution 1.0）读 `TaskExecution.DeviceIdentity`；
- `PointAccess`：点位面板与签名手动写（驱动宿主上配了点表的设备）；只读写点位的设备怎么配见 插件配置（`ilcs-devices/host/插件配置.md`）「两层」；
- `TaskExecution`：按 ILCS 指令号提交、查询、保持、终止，回执 JSON 与上面的 HTTPS JSON 契约一致。只读写点位的设备（服务没有
  实现它）在配置里写 `"tasks": false`：只欠只读级验收，下发明确拒绝；
- 服务实现了 `AuthorizationService` 就每次调用带令牌：`credential_ref` 指向令牌文件（凭据目录内的 file://）或 env://。

驱动只认 ILCS 的这几个特性，不对接厂家自带的 SiLA 特性：厂家原生 SiLA 设备要经驱动宿主映射成这份契约。现行的是 TaskExecution
1.1：上下文带工位编号，投料步骤再带物料 `{name, unit, param}`；`SubmitTask` 声明了 `NotSupported`、`DeviceUnreachable`（动作前
就连不上，设备没动），都按明确失败处理，报错文字以按错误标识定下的类别词开头（联锁 → 安全异常，无响应 → 通信异常）。

接驱动宿主的设备还有**驱动配置闸门**：接入验收通过时记下设备服务报的驱动与配置摘要（已批准）；执行器探测读到的摘要变了
（驱动项目里改了点表或映射），照配置变更处理——配置版本加一、欠验收、停派工、报警，在途指令转人工核查。这时要有工位编辑权限的人
在「设备连接」核对驱动项目里的这次改动，写明依据并签名「批准驱动配置变更」，执行器随即跑只读级验收（换了插件还要申请动作级），
验收看到的正是批准的那一份才放行。没批准时验收通过了也放不开，签名放行也不行。

驱动宿主的设备文件可以在它的**设备管理台**上在线增删改、逐台起停 SiLA 服务（本机 `http://127.0.0.1:50200`，见
`ilcs-devices/host/README.md`「设备管理台」）。对 ILCS 来说和改设备文件、重启驱动宿主一样，不另开口子：
- 改了映射（摘要变了）：照上面的驱动配置闸门处理；只改超时、配置版本、备注不变摘要。改了端口，工位连接配置里的 `port` 要跟着改。
- 停服务期间工位显示离线、执行门挡住下发，在途指令保持运行中；服务重新起来后驱动自动重连，不用在 ILCS 这边操作。
- 管理台上新加的设备，ILCS 这边照旧登记工位、填 `sila2_v1` 连接配置、过接入验收；设备详情页按宿主主机名、端口、证书和读到的
  设备身份生成这份连接配置，可以直接复制。

```json
{
  "kind": "real",
  "driver": "sila2_v1",
  "protocol": "SiLA 2",
  "config": {
    "host": "sila-sim-lh",
    "port": 50052,
    "ca_file": "/run/secrets/ilcs/sila/SIM-LH-01.crt",
    "expected_device_id": "SIM-LH-01",
    "connect_timeout_sec": 3,
    "request_timeout_sec": 10,
    "probe_interval_sec": 10,
    "device_timezone": "UTC"
  },
  "supports_hold": true, "supports_abort": true, "supports_query": true, "supports_dedup": true
}
```

- `connect_timeout_sec` 约束端口探测；探通之后建客户端（TLS、读特性清单、取特性定义）最多再等
  `connect_timeout_sec + request_timeout_sec`，等不到按连不上处理——接了连接却不应答的设备服务不会挂住执行器，
  也不会让别的工位的首次连接排在它后面（只有 sila2 现场编译特性的那一步是全进程串行的）。之后每次调用按 `request_timeout_sec`。
- 在线状态由执行器主动探测（`heartbeat_mode` 默认 `probe`），设备不用推心跳；设备身份里的
  `interlock`、`accepts_commands` 同步为工位联锁与是否接受指令。
- `insecure: true` 只允许在非正式环境使用；正式环境必须 TLS，并用 `ca_file` 指向设备证书的 CA。
- 设备身份里 `simulator: true` 的设备在正式环境被拒绝接入。
- 真机到位前可用 `ilcs-devices/simulators/` 下的外部模拟设备挂到驱动宿主上联调（每类插件都有对应的模拟设备），含断连、回执丢失、卡死等故障注入。

## 点位读数记成环境读数（`environment`）

只读写点位的传感器（温湿度计、压力表、手套箱水氧仪）可以当环境监测用：连接配置里加 `environment`，执行器探测在线时按采集周期
读这几个点，记成环境读数（区域 × 指标，来源 `device:<工位>`）。步骤写了环境要求（`environment: [{metric, min, max, zone}]`）的，
开跑检查和每个设备步骤下发前都按该区域该指标的最新读数核对：没有读数、过期、超限都不放行。

```json
"environment": {"zone": "设备模拟联调区", "interval_sec": 30, "points": {"temperature": "temperature", "humidity": "humidity"}}
```

- `zone`：区域，写工位编号（步骤不写区域时按它分到的工位取读数）或房间 / 手套箱名；`points`：环境指标 ← 点名；`interval_sec`：缺省 60 秒。
- 指标用环境监测登记的名字（`temperature`、`humidity`、`dew_point`、`h2o_ppm`、`o2_ppm`、`pressure`、`pressure_diff`、`particles`），
  单位取点表里的 `unit`。读不到、不是数的点不记（执行器日志里记一条），缺读数照样不放行。
- 改 `environment` 不用重新握手（和超时一样不改连谁、怎么判结论）；只对执行器探测的设备生效，推心跳的设备经 `/runtime/environment` 上报。

## 厂家 SDK 接口服务（只有 Windows SDK / DLL 的设备）

在设备旁的工控机上跑一个小服务：调用厂家 SDK，对 ILCS 提供上文「HTTPS JSON 网关驱动」的契约，ILCS 侧用
`http_json_v1`。服务要保证三件事：**按 ILCS 指令号去重**（重复的 `POST /commands` 回放原结论）、**按指令号查询**
（执行器重启后要能问到）、**回执丢失时宁可不回也不编造**（驱动按结果未知处理）。

这三件事由 `ilcs-devices/gateway/ilcs_gateway` 做好了（见 `ilcs-devices/gateway/README.md`）：设备开发者只实现 `Device` 的
身份、开始、读状态、保持 / 恢复 / 终止，SDK 负责去重与回放、先落盘的作业台账、按指令号查询、令牌与 TLS、模拟设备的统一控制口。
模块的目录结构、模拟接口的写法（「假的厂家 SDK」，驱动代码一行不改就能对着它测）与交付流程见
`ilcs-devices/gateway/README.md`，样板是 `ilcs-devices/gateway/sample-cycler`（ST-07 这类充放电柜）；
在设备仓库里 `python gateway/new-module.py` 从样板生成新模块，测试开箱就能过。

## 结果文件接收器（检测软件只导出文件时）

`ilcs-devices/connectors/result_files/receiver.py`：盯住导出目录，文件写完（大小与修改时间 `settle_sec` 秒不变）后按文件名规则
关联检测任务与样本，按列映射指标，先上传原始文件（`POST /api/integrations/files`）再回传结果
（`POST /api/integrations/results`）。它只解决取数，**不负责启动检测**。配置与目录约定见
`ilcs-devices/connectors/result_files/README.md`。

## 驱动必须实现的契约

每个真实驱动至少实现：

1. `healthcheck()`：验证配置、凭据可读取、网络可达、设备身份/序列号符合预期；失败抛异常。
2. `submit(request)`：携带系统生成的 `command_id`，只在设备明确接受后返回 `accepted/running/done`。
3. `query(command_id)`：按原指令查询；不支持时明确返回不支持并关闭能力声明。
4. `hold(request)` / `abort(request)`：只有设备真实支持时才声明为 `true`。
5. 回执包含原 `command_id`、设备时间、质量标记、实际下发参数；遥测注明来源。

网络无响应是 `AdapterUnreachable`（结果未知），设备明确拒绝才是 `AdapterError`（确定失败）。两者不能混用。
设备有响应但无法据此确认结果（重复投递冲突、限流、回执不合规）用 `AdapterIndeterminate`，
它是 `AdapterUnreachable` 的子类，按结果未知处理。驱动内部抛出的其他意外异常同样按结果未知处理。

### 设备方法目录（驱动自报）

「工位与接入 → 设备连接」配置里的「读取设备自报信息」调用 `POST /api/stations/{id}/adapter/describe`，读驱动的设备身份：

- HTTPS 网关的 `/health`、SiLA 2 设备服务的 `DeviceInfo` 与 `TaskSupport`（设备端程序）里带
  `vendor`、`firmware`、`model`、`methods`（`[{program, name, capability}]`）、`commands` 就按设备自报；驱动宿主上的设备按
  设备文件里登记的 `methods`（点表映射还有 `recipe.map` 的程序号）经 `TaskSupport` 报给 ILCS；
- 设备服务报不了目录的，在 ILCS 连接配置 JSON 里登记 `"methods": ["VD-120", "VD-90"]`（或对象列表），
  来源标为「按登记配置」；`vendor`、`firmware` 同样可以写在配置里。
- `program` 为 `*` 表示接受任意设备端程序（模拟器默认这样报）。

流程步骤引用设备方法时，方法的设备端程序不在目录里的工位不承接这一步；从没读过目录（空）的工位不据此排除。
设备自报的型号与工位关联资产在「仪器设备」登记的型号核对（没有资产档案的工位与工位登记的型号核对），不一致只提示、不覆盖登记值——设备方法的适用型号按登记值匹配。
设备动作指令带 `method: {id, code, version, name, program}`：HTTPS 网关在请求体里、SiLA 2 在 `ContextJson` 里，设备按
`program` 选设备上的程序（驱动宿主的点表映射按 `recipe.map` 换成 PLC 程序号；Modbus 任务寄存器仍按能力码下发，程序由 PLC
侧配置保证）。

正式环境（`ILCS_ENVIRONMENT=production`）禁止模拟适配器执行任何指令，也不允许模拟心跳：
未配置真实驱动的工位在下发时被拒（`simulation_adapter`），执行器投递时也会拒绝。

## 接入验收

驱动配好之后，用同一套检查清单验收，报告存档作为上线证据。清单分三级：

| 级别 | 检查项 | 会不会让设备动作 |
|---|---|---|
| 只读 | 设备身份与方法目录、健康检查、契约声明、查询不存在的指令号 | 不会 |
| 动作 | 正常完成、同一指令号重复提交、重建驱动后按指令号查回、保持、终止 | 会：真实设备要签名并写明现场批准人（DEC-02） |
| 故障 | 回执丢失、设备忙、联锁、失联 | 会；只对自报为模拟器、登记了模拟设备控制口的设备，正式环境不跑 |

**在界面上跑**：「工位与接入 → 设备连接 → 连接配置 → 接入验收」。申请只登记一条排队记录，由执行器执行（它是唯一驱动设备的进程，
验收不会和投递、轮询抢同一台设备）；报告入库、出了结论就不能改，可下载 Markdown，带驱动、固件、配置版本与摘要、模板版本。
动作级等工位上没有在动作的指令才开始，排队期间新的动作指令先不投递。

**配置变更后的闸门**：改了配置的真实设备先「待接入验收」——挡住排程与下发（执行门的 `blocked_stations`），执行器自动跑一次只读级，
通过了才重新接指令。第一次接成真实设备、换了驱动还欠动作级（自报为模拟器的设备只读级就够；只读写点位、不参与自动流程
（`tasks: false`）的设备也只欠只读级）。设备当时连不上导致没通过的，
恢复在线后自动再跑一次。迁移前在用的配置不追溯。

**命令行**（按库里的工位，或不连 ILCS 库、只给一份适配器登记 JSON——设备开发者在自己电脑上用）：

```bash
docker compose exec api python ../scripts/device-acceptance.py ST-05
docker compose exec api python ../scripts/device-acceptance.py ST-07 --physical --confirm ST-07 --output /data/acceptance-ST-07.md
python scripts/device-acceptance.py --adapter my-gateway.json --allow-host --physical --faults --json report.json
```

- 验收指令编号以 `ACC-` 开头；工位上还有可能在动作的指令时拒绝运行。
- 命令行按工位跑动作级时**不挡投递**：在用的工位请从界面申请（执行器执行，排队期间挡住新指令）；命令行动作级只用于
  停用的工位或不连库的独立验收。
- 缺省的能力与参数依次取：设备接入模板的验收缺省 → 适配器配置里的 `"acceptance": {"capability", "params"}` →
  工位第一个能力、参数取工位极限的中点。转运这类极限里没有的参数（起止位置 `from` / `to`）只能从前两处来；
  界面的动作级申请里另有「其他参数（JSON）」可改。命令行用 `--capability` 与 `--params '{"mass": 0.0152}'` 指定。
  缺省参数同样按工位极限核对，越界就不申请。
- 每个动作项目最多等 `ILCS_ACCEPTANCE_POLL_TIMEOUT_SEC`（缺省 180 秒）：要比验收用的那个动作长。
- 保持项目：保持一个在途动作后先续跑到做完（生产上保持之后就是续跑；有的设备保持的是整机，只终止作业不会回到就绪），
  续跑不了再终止。
- 验收指令收尾：结束时还没结束的 `ACC-` 指令逐条终止，停不下来的记「验收指令收尾」不通过，工位改回欠动作级。
- 「重复提交只动作一次」要读得到设备侧的动作次数才判通过：设备认 ILCS 指令号时按指令号数，不认的（串口命令、PLC 点表、车队）
  数设备的总动作次数；读不到判「跳过」，由现场核对设备记录。
- **模拟设备统一控制口**：试点的每台模拟设备都开了控制口（9900，`ilcs-devices/simulators/common/control.py`），适配器配置里用
  `"simulator_control": {"url": "http://<模拟器>:9900", "token_ref": "file:///run/secrets/ilcs/simctl/<设备>.token"}` 登记
  （车队再加 `"unit": "AGV-01"`）；HTTPS 网关模拟器不登记也行，控制接口就在它自己的 API 上。接真机时删掉这一项。
  控制口报的 `unsupported` 是这台模拟设备注入不了的故障（点表设备没有回执可丢），对应项目判跳过。
- 提交只是交接的驱动（PLC 点表写下启动沿）：设备忙、联锁的拒绝是设备之后才判断的，故障项目等它回写成
  失败、设备没动作才算通过。
- 真实设备的回执丢失要在网络路径上注入（中间代理丢应答），不能靠设备配合。
- 报告只给配置摘要，不含凭据与配置原文；退出码 0 表示没有不通过的项目。
