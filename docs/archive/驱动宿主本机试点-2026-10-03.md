# 驱动宿主本机试点记录

> **历史文档（2026-10-03）**：设备驱动移出 ILCS（阶段 1）的本机试点证据，不代表当前实现；现状以代码和
> `devices/host/README.md`、`devices/contracts/sila2/README.md` 为准。

- 日期：2026-10-03
- 环境：本机 Docker Desktop。ILCS（api、executor、web、db）按 `deploy/` 部署，库版本 `0050_driver_config_gate`；
  驱动宿主 `ilcs-driver-host` 按 `devices/host/deploy/compose.yml` 起，现场目录 `data/driver-host/site`（`sites/protoforge` 的副本）；
  sila2 0.14.0，Python 3.11
- 设备：ProtoForge（`suoten/protoforge`，1.4.2）上的 OPC UA 压力传感器、HTTP REST 传感器、从站 2 握手 PLC
- 连接：ILCS → `driver-host:50201/50202/50203`（每台设备一个 SiLA 服务，自签证书 TLS，每次调用带 `AccessToken`）→ ProtoForge
  （Modbus 与 OPC UA 经 `host.docker.internal`，HTTP 设备的 8080 经 `ilcs_backend` 网络）
- 部署前备份：`data/backups/pre-driver-host-20261003-145412`（库转储、web/dist、env），旧镜像 `ilcs-api:pre-driver-host-20261003-145412`

## 结果

### 1. 部署

- 部署前备份库、`web/dist` 与 `deploy/.env`，给旧镜像打标签；ILCS 与驱动宿主的镜像都从干净检出（`git archive`）构建。
- `deploy/.env` 的设备主机白名单加 `driver-host`；`docker network connect ilcs_backend protoforge`（HTTP 设备的 8080 只在
  ProtoForge 自己的网络里）；库迁移到 `0050_driver_config_gate`。
- 驱动宿主起来后 `python -m ilcs_host --site /site --check` 列出三台设备的插件、端口、特性与配置摘要；ILCS 的 api、executor
  重建后健康检查正常。
- 试点中修正后又重新部署了四次（两次全部重建，两次只换驱动宿主），最后是 ILCS 镜像 `b10e51c`、驱动宿主 `3847d45`；每次都从
  干净检出构建，替换 `web/dist` 之前先备份（`data/backups/pre-pilot-fixes-*`），没有新迁移。

### 2. 接入（`scripts/load-driver-host-pilot.py register`）

| 工位 | 设备服务 | 结果 |
|---|---|---|
| ST-PF-OPCUA | `driver-host:50202`，opcua_map，只读写点位 | 只读级验收通过，批准驱动配置 `sha256:17333515eabf…` |
| ST-PF-HTTP | `driver-host:50203`，rest_map，只读写点位 | 只读级验收通过，批准驱动配置 `sha256:4115f4022c75…` |
| ST-PF-MB | `driver-host:50201`，modbus_map，点位 + 任务 | 设备身份不匹配（期望 PF-MB-PLC-01，实际缺失）：见「没做的与遗留」 |

### 3. 经 ILCS 读写点位

- 读：OPC UA 五个点（压力、温度、高报、低报、压力设定）、HTTP 四个点（温度、湿度、气压、状态）都读到；名称、单位、
  可写范围来自驱动宿主的 `PointAccess.Points`。
- 签名手动写：OPC UA `setpoint` 5.0 → 6.0、HTTP `humidity` 71.69 → 55，执行器写入后回读一致。
- 越界：`setpoint = 20` 在申请时就被拒（422 `point_write_refused`），范围 0–10 取自驱动宿主报的点位目录。

### 4. 直接调用驱动宿主

在 ILCS 执行器容器里用 SiLA 客户端（走 `ilcs_backend` 网络、校验驱动宿主证书）：

| 调用 | 结果 |
|---|---|
| 不带令牌 | SiLA 框架直接拒绝（缺 `AccessToken` 元数据） |
| 令牌不对 | `InvalidAccessToken` |
| 绕过 ILCS 写 `setpoint = 20` | `OutOfRange` |
| 写字符串 | `InvalidValue` |
| 写只读点 `pressure` | `NotWritable` |
| 同一个 `RequestId` 重发 | 回放原结论，没有再写 |
| 同一个 `RequestId` 换一个值 | `RequestConflict` |
| 只读写点位的设备 | 没有 `TaskExecution` 特性 |
| ILCS 驱动连错设备（50203 当成 PF-OPCUA-PRESSURE） | 设备身份不匹配：期望 PF-OPCUA-PRESSURE，实际 http-rest |
| ILCS 不配 `credential_ref` | 明确失败：设备服务要求令牌 |
| 只读写点位的设备配成参与自动流程 | 健康检查失败：设备服务没有实现 TaskExecution |

### 5. 设备断连（`docker pause protoforge`，约 75 s）

- 执行门拦下两台（适配器失联），各报一条「设备适配器失联」；`docker unpause` 后 5 s 内放开，报警条件复位，确认与关闭留给人。
- 发现两处问题（修法见下一节）：
  - 经 ILCS 读点位，等满 10 s 后返回 500 服务器内部错误；
  - 断连时的签名手动写（`685d0121`）记成「结果未知」，恢复后读回仍是 5.0。驱动宿主其实在「读当前值」那一步就失败了，
    根本没写；但它逐点等超时，答复晚于 ILCS 的 10 s 截止时间。
- 修复后（`b10e51c`）重演：OPC UA 读点 5.1 s、HTTP 读点 6.7 s 就答复，第一个点报超时，其余报「设备没有回话……没有再读」；
  断连时的签名手动写（`bb40bd7f`）明确记「没有写入（DeviceUnreachable）：读不到 setpoint 的当前值」，恢复后读回 5.0，与记录
  一致；执行门与报警同上。

### 6. 只改驱动

在驱动宿主的现场目录里改 `PF-OPCUA.json`（压力设定上限 10 → 12 bar，配置版本 r1 → r2），只重启驱动宿主，ILCS 的配置一个字没动：

| 时间 | 发生了什么 |
|---|---|
| 0 s | 改设备文件；`--check` 算出新摘要 `1e11c803…`；`docker restart ilcs-driver-host` |
| 9 s | 执行器探测读到新摘要：ST-PF-OPCUA 配置 v2 → v3、欠只读级验收、停派工；报警 A-1082「设备服务的驱动配置变了（opcua_map 17333515 → opcua_map 1e11c803）」；手动写点被拒（409 `driver_change_unapproved`） |
| 9 s | 工程师核对后签名批准（`批准驱动配置变更`），排了一次只读级验收（trigger `driver_change`） |
| 11 s | 验收通过，验收看到的摘要正是批准的 `1e11c803…`，闸门放开；点表上限变成 12，签名写 11.0、再写回 5.0 都成功 |
| 之后 | 下一次探测摘要一致，报警 A-1082 条件复位 |

整个过程 ILCS 的 api、executor、web、db 容器都没有重启（启动时间、重启次数不变），只有驱动宿主重启。

回滚（上限 12 → 10，版本 r2 → r1）同样是一次驱动变更，同样停派工、拒绝手动写、签名批准后验收放行。回滚时脚本把上限写成了
浮点数 10.0（原文件是整数 10），算出的摘要 `55003585…` 和原来的 `17333515…` 不同：配置摘要按规范化 JSON 区分数值类型，
10 和 10.0 算两份配置。方向是保守的（最多多批准一次），不改。最后把仓库里 `sites/protoforge` 的原文件拷回现场目录，再批准一次，
ST-PF-OPCUA 停在配置 v5、批准的摘要回到 `17333515…`。

## 试点中发现并修掉的问题

1. **读点位逐点等超时**：设备不回话（连不上、超时，且确实等了大半个超时）就不再读后面的点，只等一个超时；设备很快回了错
   （地址不对、节点不存在、HTTP 5xx）仍只算那一个点。驱动宿主和 ILCS 里的两份插件一起改。
2. **OPC UA 断网后关旧会话又等一个超时**：会话建好之后断网（连接还挂着、没有回音），超时之后丢弃会话时要给服务器发
   CloseSession，又等满一个超时。改为后台关：这次调用马上答复；服务器还在的话照样关干净，不留孤儿会话占服务器的会话数。
   两份一起改。
3. **ILCS 读点位报 500**：设备服务没在截止时间内答复，改为 409 `device_unreachable`；被拒是 409 `point_read_refused`。
4. **驱动配置变了还没批准，手动写点照样能申请、能执行**：新点表可能已经把同一个点名指到了别的地址。改为申请时拒绝
   （409 `driver_change_unapproved`），执行器执行前再核一遍，界面上的「写入…」置灰并说明原因。
5. **设备报空身份时拿配置顶替**：插件映射了设备编号、设备却报空时，驱动宿主拿现场配置里的 `device_id` 顶上，还报来源
   「config」，接错的设备就核对不出来了。改为以设备为准、报缺失；映射里没有编号的设备才按配置登记。
6. **`--check` 改了状态**：配置摘要原来在构造设备运行时就记下，`python -m ilcs_host --check` 检查过新配置就算换过了；
   旧进程随后又开了作业的话，换配置重启时「在途作业时不许换配置」核对不出来。改为设备服务按这份配置上线后才记。
7. **驱动宿主日志被 sila2 淹没**：sila2 每次属性读取按 INFO 记三行，日志器按特性名起；三台设备每个探测周期都读，40 s 三百多行。
   改为第三方库只记 WARNING 以上，宿主自己的记 INFO。
8. **超时怎么配**写进 `devices/host/README.md` 与契约说明：ILCS 的 `request_timeout_sec` 要长于驱动宿主一次调用的最长时间，
   大约是插件的 `connect_timeout_sec + request_timeout_sec`。

第 1–6 条都有用例（`devices/host/tests`、`api/tests/domain/test_silent_device.py`、`api/tests/api/test_driver_host_points.py`；
断网用一个能「冻结」的 TCP 代理模拟），撤掉修复时这些用例都失败；第 7 条只调日志级别，第 8 条是文档。ILCS 全量回归
（`b10e51c`）992 通过、1 跳过；最后一条修正（`3847d45`）只改驱动宿主，驱动宿主 20 条用例、ILCS 经驱动宿主的 8 条用例通过。

## 没做的与遗留

- **ST-PF-MB（握手 PLC）的动作级验收、任务中途重启驱动宿主的演练没做**。ProtoForge 日志显示，从站 2 的场景
  `ilcs-plc-modbus` 在 10-02 21:18 被手动停止、21:46 被删除；ILCS 的失联报警 A-1069 也是 21:46。此后 ProtoForge 对每个从站号
  都回 0，与这次部署无关。重新导入并启动 `devices/simulators/protoforge/ilcs-plc-scenario.json` 后，再跑
  `scripts/load-driver-host-pilot.py register --only ST-PF-MB --acceptance`。
  重启后按台账查回、不重发，由 `devices/host/tests` 与 `api/tests/domain/test_driver_host.py` 覆盖（真实 Modbus TCP 模拟 PLC）。
- **新登记或改了连接配置的工位，会先报几秒「设备适配器失联」**：在等执行器握手。条件随后复位，但报警留着等人确认。
  这是 ILCS 原有行为，10-02 用 modbus_map_v1 登记 ST-PF-MB 时也报过（A-1068），另开任务处理。
- 手动写点「结果未知」之后怎么核对（`QueryWrite`）、服务器证书缺 SiLA 的服务器 UUID 扩展：记入契约的待评审第 7、8 条。
- 本机试点里，驱动宿主的私钥与令牌表（`secrets/host/`）和 ILCS 的凭据都在同一个 `secrets/` 下，ILCS 的容器也挂得到。
  正式部署时驱动宿主在另一台机器上，ILCS 这边只放 `driver-host.crt` 和自己的令牌。
- ProtoForge 的状态：HTTP 设备的湿度停在演练写入的 55；OPC UA 设定值已写回 5.0。
- 演练与重新部署留下的报警（适配器失联、驱动配置变了）条件都已复位，等人确认、关闭。
